# Content style

These rules apply to every page in `content/`. Feedback on published pages is
added here as it comes, under [Feedback](#feedback).

## Hard rules

1. **Every page says it is AI-generated.** Its front matter has
   `aiGenerated: true`, and the website shows a banner on the page.
2. **Pages are AI-generated by Claude from the repository and CI, and say
   nothing more about who made them.** No page, and nothing in `content/`,
   says or implies that a person reviewed, edited or approved it.
3. **Every factual claim has a source.** The source is a file in this
   repository, a pull request, an issue, a CI run or a release, and the
   page's `sources` lists it. Numbers are copied from the source and never
   estimated. If a source and the code disagree, the page doesn't make the
   claim until the source is corrected.
4. **Say nothing negative about others.** That covers other projects,
   companies, platforms and people. Describe what Lasm does. Don't compare
   Lasm to others to their discredit. An upstream bug is described as
   behaviour, with its upstream report if there is one.
5. **Promise no future features.** Describe what exists. A change that is
   merged or in review but not yet released is labelled with its version and
   PR ("coming in 0.3.9, PR #47"), and only when that release is already being
   prepared.
6. **Don't publish unfixed security issues.** A bug that could harm users is
   written up only after its fix is released.
7. **Make no legal or pricing claims.** Don't interpret licences, terms or
   compliance, and don't state prices, plan limits or costs. Linking to
   [LICENSE](../LICENSE) and the README's licence section is fine.
8. **Make corrections in the open.** A wrong page is fixed by a new commit, and
   the page ends with a dated note: "Corrected on YYYY-MM-DD: …". Pages are
   not quietly rewritten or deleted.
9. **Tutorials are tested.** Every command, file and output in a tutorial
   is checked by `scripts/content/check-tutorials.mjs` in CI. If it can't be
   checked, it isn't in the tutorial.

## Voice

- Plain and concrete. Use short sentences, one idea each.
- Technical and exact. Name the file, the command, the version, the PR.
- Don't use hype words (revolutionary, blazing, seamless, game-changing,
  magic). Don't add exclamation marks, emoji or filler.
- Say what was measured or checked, how it was checked, and its limits.
  "Tested in CI with wrangler dev (local workerd)" is better than "works on
  Cloudflare".
- Write "we" for the Lasm project. Address the reader as "you" in tutorials.
- Show the code that runs, and the output it actually prints.
- A bug write-up covers how the bug was found, the smallest reproduction,
  the cause, the fix, and the test that keeps it fixed.

## Links

- Link to files in this repository with relative paths
  (`../../docs/TESTING.md`). The website rewrites them to github.com.
- Link to everything else with full `https://` URLs.
