## Decisions in detail (0.7 stream)

Entries `0.7-n`: everything a user types or configures outside Lean code
(commands and flags, target names, environment variables, configuration, the
output layout, `lasm init` and `npm create @lasm`). The rule for every one:
one consistent, minimal CLI that does what each platform expects.

### 0.7-1 and 0.7-16: One help text, and no `lasm version` (CLI)

- **Decision:** `lasm --help` (`-h`, and `--help` after any command but
  `init`, `dev` and `package`, which have their own) prints one text,
  `cliUsage` in src/cli-arguments.mjs, built from the same target tables the
  parser uses. The bare word `lasm version` is no longer a command; the version
  is `lasm --version` or `lasm -v` (npm's, Node's, Bun's and Deno's spelling).

  ```sh
  npx lasm --help        # every command, the targets of build and package, what --output names
  npx lasm --version     # lasm 0.9.0 (@lasm/cli; Lean 4.35.0; Node 26.13.1; linux-x64)
  npx lasm version       # Unknown command "version". Commands: build, run, dev, init, package, editor, cache; …
  ```
- **Why:** there were two help texts (a release candidate printed a second,
  hand-written one with different target lists), and three spellings of the
  version. Alternatives: keep `lasm version` as an alias (redundant; no
  platform CLI Lasm sits beside has both).
- **Where:** PR #304 (milestone 0.7); released in 0.9.0.
- **Status:** signed off by Jordan (2026-11-24).

### 0.7-2: `lasm build` takes one source; `--output` names the output (CLI)

- **Decision:** the positional output alias is removed.

  ```sh
  npx lasm build Main.lean --output dist     # was also: npx lasm build Main.lean dist
  npx lasm build Main.lean dist              # Unexpected argument "dist": lasm build takes one Lean source. Name the output with --output.
  ```
- **Why:** two ways to say one thing, and a second word that silently became a
  directory. Every other command names its output with `--output`. Migration
  note in docs/release/0.9.0-notes.md.
- **Where:** PR #304; released in 0.9.0. **Status:** signed off by Jordan (2026-11-24).

### 0.7-5 and 0.7-4: `--output` always names what the target writes for deployment (CLI, output layout)

- **Decision:** with `--target node` (the default under Node) `--output` names
  the Node build (default `dist/`, which `lasm package` reads). With every
  other target it names what is deployed, default the platform's own place,
  and the Node build that is made from stays in the build cache
  (`.lake/lasm/`). This extends Jordan's decision of 2026-11-04 (for the edge,
  WASI and browser targets, 0.5.0) to the function platforms.

  | Target | Default output |
  | --- | --- |
  | `node` | `dist/` |
  | `lambda`, `lambda-edge` | `lambda.zip`, `lambda-edge.zip` |
  | `vercel`, `netlify` | `.vercel/output`, `netlify/functions/lasm` |
  | `azure-functions`, `cloud-functions` | `azure-functions/`, `cloud-functions/` (named `azure` and `gcf`, output `gcf/`, until 0.7-24) |
  | `workers`, `bun`, `deno`, `deno-deploy` | `workers/`, `bun/`, `deno/`, `deno/` |
  | `supabase-edge` | `supabase/functions/<name>/` |
  | `vercel-edge`, `netlify-edge` | fixed by the platform (`api/`, `netlify/`); `--output` refused |
  | `wasi`, `wasi-http`, `fastly` | `wasi/`, `wasi-http/`, `bin/` and `pkg/` |
  | `browser` | `dist/` |

  ```sh
  npx lasm build Main.lean --target lambda --output app.zip   # writes app.zip; no dist/
  npx lasm build Main.lean && npx lasm package --target lambda  # dist/ and lambda.zip, as before
  ```
- **Why:** `--output` meant the Node build for six targets and the deployable
  for twelve. Now one rule. Alternative: keep `dist/` for function
  platforms (inconsistent, and `lasm package` already covers "a Node build and
  a package").
- **Where:** PR #304; released in 0.9.0. **Status:** signed off by Jordan (2026-11-24).

### 0.7-23: The same option rules and error shapes in every command (CLI, errors)

- **Decision:** every command refuses a repeated option with
  `Specify --<option> only once` and `--dev` with `--release` with
  `Choose one of --dev and --release` (`lasm dev` and `lasm init --template`
  now do, as `lasm build` did). An unknown name in a list (`--target` of
  `lasm build` and `lasm dev`, `lasm init --template` and `--deploy`) is
  refused with the list and the closest name, or the name another platform
  spelling means (`cloudflare` → `workers`), when there is one.

  ```sh
  npx lasm dev --target worker     # Unknown lasm dev target "worker" (did you mean --target workers?). Choose one of: node, bun, …
  npx lasm dev --release --dev     # Choose one of --dev and --release
  npx lasm init app -t Hono        # Unknown template "Hono" (did you mean --template hono?). Choose one of: plain, …
  npx lasm init app --deploy cloudflare   # Unknown deploy target "cloudflare" (did you mean --deploy workers?). Choose one of: lambda, …
  ```
- **Why:** the commands disagreed (last one silently won in `lasm dev` and
  `lasm init`; only `lasm build` suggested names). Each is in the Lean models
  (verification/cli/Lasm/Cli/Model/) and the model differential, and the
  error corpus prints each.
- **Where:** PR #304; released in 0.9.0. **Status:** signed off by Jordan (2026-11-24).

### 0.7-9 and 0.7-8: Each `lasm init --deploy` name is the target it builds

- **Decision:** `--deploy <name>` adds the platform's files and
  `npm run build:<name>`, which runs `lasm build --target <name>`. So
  `--deploy lambda` is now the Lambda `.zip` (it was `lambda-zip`), and the
  container image, which is not a `lasm build` target, is
  `--deploy lambda-container` (it was `lambda`). `spin` stays: it names the
  platform and builds `--target wasi-http` (`spin.toml`, `npm run build:wasi-http`).
  `lambda-zip` is refused like any unknown name, with no hint of its own
  (no compatibility hints, Jordan 2026-11-24; removed in PR #384).

  ```sh
  npm create @lasm@latest my-fn -- --template hono --deploy lambda             # npm run build:lambda → lambda.zip
  npm create @lasm@latest my-fn -- --template hono --deploy lambda-container   # Dockerfile.lambda
  ```
- **Why:** `--deploy lambda` and `--target lambda` meant different things (a
  container image and a zip). Alternative: keep `lambda-zip` (two names for
  the one target). The container image's serving, then the AWS Lambda Web
  Adapter (a loopback adapter), was replaced in 0.9.0: the image is Lambda's
  own Node base image calling the handler (0.2-11, #322).
- **Where:** PR #316; released in 0.9.0. **Status:** signed off by Jordan (2026-11-24).

### 0.7-24: Function-platform targets named after the platforms

- **Decision:** `azure` becomes `azure-functions` and `gcf` becomes
  `cloud-functions` (output `cloud-functions/`), everywhere a target is named:
  `lasm build --target`, `lasm package --target`, `lasm init --deploy` and its
  `npm run build:<target>` script. Every other target keeps its name: each is
  the platform's product as its own docs and CLI call it (`lambda`,
  `lambda-edge`, `vercel`, `netlify`, `workers`, `vercel-edge`,
  `netlify-edge`, `deno-deploy`, `supabase-edge`, `fastly`, …). The old names
  are refused like any unknown name, with no hint of their own: no
  compatibility hints (Jordan 2026-11-24, item 15; removed in PR #384). The
  platforms' own names `google-cloud-functions` and `cloud-run-functions`
  suggest `cloud-functions`. `lasm package`'s unknown-target error names the closest target, as
  every other command's does.

  ```sh
  npx lasm build Main.lean --target azure-functions    # azure-functions/
  npx lasm build Main.lean --target cloud-functions    # cloud-functions/
  npx lasm build Main.lean --target cloud-run-functions  # Unknown build target "cloud-run-functions" (did you mean --target cloud-functions?). …
  npx lasm package --target gcf                        # Unknown package target "gcf". Choose one of: …
  ```
- **Why:** `gcf` was an abbreviation and `azure` a cloud, not a product; the
  deployment guides were already `docs/deploy/azure-functions.md` and
  `docs/deploy/cloud-functions.md`, and the Azure output directory already
  `azure-functions/`. Alternatives: `google-cloud-functions` (longer, and
  Google now calls it Cloud Run functions while its CLI keeps
  `gcloud functions`); keeping the old names as aliases (two names for one
  target).
- **Where:** PR #339; released in 0.10.0.
  **Status:** signed off by Jordan (2026-11-24).

### 0.7-25: The editor uses the project's own Lean; Lasm leaves elan alone (issue #343)

- **Decision:** No lasm command sets an elan override or links an elan toolchain.
  Lasm 0.3.0 to 0.10.0 did both:
  - `lasm editor`, and after a good build `lasm build`, `lasm dev` and
    `lasm init`, linked Lasm's managed Lean as the elan toolchain
    `lasm-4.35.0-<prefix>`;
  - they set it as the project directory's elan override.

  The Lean editor now runs the project's own toolchain, the one `lean-toolchain`
  names. That is Lean 4.35.0, the release Lasm downloads, with the same commit,
  so Lasm's `.olean` files load in it. It finds `Lasm.*` through Lasm's Lake
  package (0.3-7): `[[require]] lasm`, path `.lake/lasm-library`. Lake puts that
  package's build directory on the editor's search path and builds the modules
  compiled on first import.
  - **`lasm editor`:** without a `lake-manifest.json`, lets Lake resolve the
    workspace first (the editor's `lake setup-file` never writes the manifest).
    Then it adds the require (as before), makes the link, writes
    `lean-toolchain` (`leanprover/lean4:v4.35.0`) when the project has none, and
    exits 0. Without elan it prints how to get it and exits 1.
  - **After a good `lasm build` or `lasm dev`, and `lasm init`:** when the project
    imports `Lasm.*` but its lakefile lacks the require, they say once to run
    `npx lasm editor`. They no longer provision or check a C tier for the editor.
  - **Existing users:** no lasm command reads or changes elan's settings. An
    override an older Lasm set stays until the user runs `elan override unset`
    in the project; the release note says so in one line. Jordan, 2026-11-24
    (item 15 of the Stage 0 answers): no code that exists only for old
    versions, so the automatic removal #373 first shipped was taken out.

  ```sh
  npx lasm editor    # adds the require, links .lake/lasm-library, writes lean-toolchain
  lake build         # a lean_exe compiles with Lean's own clang
  ```
- **Why:** issue #343. Since #86 (issue #72), the override toolchain carried
  Lean's C compiler only when a Lake package had C code. Every `lean_exe`
  compiles through C too, so after `lasm build` a native `lake build` fell back
  to `cc` on `PATH`, or failed where there was none. With a system `cc`, it
  built against Lasm's headers instead of Lean's own clang. A per-directory
  toolchain switch also changed what plain `lake` meant for the user's native
  code, tests and CI scripts, which is exactly what Lasm should not touch (do
  what the platform expects: elan and `lean-toolchain` choose Lean). Since 0.3-7
  and #338 the override no longer did anything for the editor:
  - Lasm's library reaches Lake through the Lake package;
  - the official toolchain and Lasm's prefix share the Lean commit, so Lake
    reuses either's build outputs (verified: the language server under
    `leanprover/lean4:v4.35.0` resolves `import Lasm.JS` and builds
    `Lasm.JS.Web.Badging` on first import).

  Alternatives:
  - **Removing an older Lasm's override automatically** (#373 as first merged:
    every command read elan's `settings.toml` and ran `elan override unset` for
    a `lasm-<version>-<hash>` toolchain). Rejected: code that exists only for
    old versions.
  - **The override toolchain always with Lean's C compiler** whenever the project
    has a `lean_exe` or other C (the issue's first option). It is more to
    download and keep (the C tier). It still switches the toolchain under the
    user's native builds. And it must track every way Lake compiles C (a
    `lean_exe`, `precompileModules`, `extern_lib`, `moreLinkObjs`, targets
    added in later Lake versions).
  - **Setting the override only in `lasm editor`** (the issue's second option).
    This still breaks native builds once a user runs it.
- **Where:** `src/editor.mjs` (`setupEditor`, `runEditor`) and `src/init.mjs`;
  the automatic cleanup removed in PR #384; tests:
  - `test/editor.test.mjs` and `test/editor-setup.test.mjs`;
  - `scripts/templates/editor-templates.mjs`. Its `lean-exe` project is
    `lake new hello exe` with a `cc` on `PATH` that fails. A native `lake build`
    works before and after `lasm build`, which sets no override. Every template opens in the language
    server with the project's own toolchain.

  Docs: [GETTING_STARTED.md](../../GETTING_STARTED.md#editor) and the README.
  Release: next. **Status:** signed off by Jordan (2026-11-24).

### 0.7-17: One shape for every error, and the exit status

- **Decision:** the messages a user can trigger follow four shapes, the same
  in every command, and each is checked by the error corpus:

  ```sh
  npx lasm dev --target worker        # Unknown lasm dev target "worker" (did you mean --target workers?). Choose one of: node, bun, …
  npx lasm init app --deploy heroku   # Unknown deploy target "heroku". Choose one of: lambda, lambda-container, …
  npx lasm init app --deploy          # --deploy requires a value (then the usage)
  npx lasm dev Main.txt               # Expected a Lean source file (Main.lean), not Main.txt
  ```

  Changed here: `lasm dev`'s unknown target (was `lasm dev --target accepts …,
  not "x"`), `lasm init --deploy`'s unknown target (was `--deploy accepts …`
  with the usage) and its missing value (now its own message, as
  `--template`'s), `lasm package`'s unknown target (`Unknown package
  target`), and `lasm dev`'s non-Lean source (now the build's wording). A
  dead branch for installs without the browser target is gone.
  Exit status: 0 on success and for `--help` and `--version`; 1 for every
  Lasm error (usage, build, missing tool); `lasm run` returns the program's
  own status, or 128 plus the signal's number.
- **Why:** each command had grown its own wording. One exit status for every
  Lasm error, as npm, Node, Bun and Deno use; nothing scripts against the
  difference between a usage and a build error.
- **Where:** PR #353; released in 0.10.0. **Status:** signed off by Jordan (2026-11-24).

### 0.7-19: `@lasm/cli` exports exactly what is public

- **Decision:** the package's `exports` map lists `./vite`, `./vite/client`,
  `./lean` and `./package.json`, and nothing else: the wildcard `./*` is gone,
  so `@lasm/cli/src/…` no longer resolves. `@lasm/cli/lean` is new: Lasm's own
  Lean, for tools that check a project's proofs with the Lean the build uses.

  ```js
  import { lasmLean } from '@lasm/cli/lean';
  const { lean, lake, version, libraryDirectory } = await lasmLean('Conduit.lean', {
    progress: ({ stage }) => stage && console.error(`[lean] ${stage}`) });
  execFileSync(lake, ['build', 'Proofs'], { cwd: root });
  ```
- **Why:** with `./*`, every internal module was importable and so part of the
  API. The apps' proof checks were the only importers (of
  `src/managed-lean.mjs`'s `provisionLean`); they need the paths of Lasm's
  `lean` and `lake`, which is all `lasmLean` returns. Alternatives: a
  `lasm lake …` pass-through command (a new command for one use; the apps
  also need the library directory and the version); keeping
  `./src/managed-lean.mjs` as an export (an internal module, with options that
  are not meant for users).
- **Migration:** `const { provisionLean } = await import('@lasm/cli/src/managed-lean.mjs'); const l = await provisionLean(file, { modules: 'extended', progress })`
  → `const { lasmLean } = await import('@lasm/cli/lean'); const l = await lasmLean(file, { progress })`
  (`l.lean`, `l.lake` and `l.version` as before; `l.libraryDirectory` is
  `dirname(dirname(l.lake))/lib/lean`).
- **Where:** PR #353; released in 0.10.0. **Status:**
  signed off by Jordan (2026-11-24).

### 0.7-7: `lasm package` removed; `lasm build --target` is the one way to build

- **Decision** (Jordan, 2026-11-24: "I don't want lasm package as an API"):
  the `lasm package` command is deleted, with its usage text and `--help`.
  There is one way to build for a platform, `lasm build <Main.lean> --target
  <target>`; for the function platforms it already built and packaged in one
  step. The two things only `lasm package` did move into the build:
  - `lasm build --target browser` checks its output against
    `lasm-manifest.json` (every file's SHA-256, and that the `.br` and `.gz`
    copies decompress to it) and writes `_headers` (immutable caching of the
    content-hashed files, the Wasm MIME type) for Netlify and Cloudflare
    Pages. A `_headers` of the project's own, from `public/`, is kept.
  - Azure Functions and Cloud Functions load their own npm package
    (`@azure/functions`, `@google-cloud/functions-framework`). The app lists it
    in its `package.json` dependencies, as each platform's own docs do, and the
    build deploys it with the app's other dependencies; `lasm init --deploy
    azure-functions|cloud-functions` adds it. Lasm installs and injects
    nothing. Without it the build stops: `This target needs the npm package
    @azure/functions: add it to package.json's dependencies (npm install
    @azure/functions), then lasm build again.`

  ```sh
  npx lasm build Main.lean --target lambda             # lambda.zip
  npx lasm build Client.lean --target browser          # dist/, checked, with _headers
  npx lasm package --target lambda                     # Unknown command "package". Commands: build, run, dev, init, editor, cache; …
  ```
- **Why:** with `Lasm.target` (0.6-20) a build is linked for one target, so
  packaging a Node build for a platform would report the wrong target; and two
  commands that produce the same deployment are one more API to learn, test
  and keep. No alias, deprecation notice or hint for the old command (no
  compatibility baggage, Jordan 2026-11-24); an unknown command gets the
  generic message.
- **Alternatives:** keep `lasm package` and refuse a build linked for another
  target (what PR #388 first did); keep it for the browser check only.
- **Where:** PR #388; released in 0.11.0. **Status:** decided by Jordan (2026-11-24).

### A55: no WASI reactor build in Stage 0

- **Decision:** declined for now. Lasm adds no `--reactor` flag and no
  `wasi-reactor` target. `--target wasi` builds WASI command programs, run once
  per process through `_start` (CLI and batch programs, Jordan, 2026-11-16).
  `--target wasi-http` keeps its own export, the wasi:http incoming handler,
  which the host calls once per request on one instance.
- **Why:** the only user so far is Lasm's own glue program
  (docs/proposals/M6_GLUE.md). There a reactor would save the runtime's
  start-up on each call, about 2 ms of a 12 ms warm call. That is an internal
  speed-up, not a user's need, and it would add a public flag, a second WASI
  ABI and its tests to sign off before 1.0. Stage 2's backend work may also
  change how the glue runs.
- **What a later reactor needs:** a concrete case of a host embedding a Lean
  program and calling it many times. Then:
  - the shape: a target or flag, and whether `main` is rerun (`lasm_run`) or
    exported Lean functions are called (an `@[export]` byte-buffer ABI);
  - `_initialize` running Lean's runtime and module initializers exactly once;
  - per-call stdin, stdout and exit status;
  - a conformance fixture under wasmtime and `node:wasi`, like the wasi-http one;
  - an evidence level in the platform table.
  The proposal with its numbers stays in [REVIEW.md](../../REVIEW.md#the-cli-surface)
  and M6_GLUE.md.
- **Where:** this entry only; no code. **Status:** signed off by Jordan (2026-11-24).
