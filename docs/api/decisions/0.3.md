## 0.3 `Lasm.JS.Web`

| Id | Surface | Current shape, with an example | Status |
| --- | --- | --- | --- |
| 0.3-1 | `Lasm.JS.Web.*` | **Jordan, 2026-11-16: the generated sources as they are.** `Lasm.JS.Web` is the entire web platform of the pinned `@webref/idl`: every interface, namespace, dictionary and member of every spec (about 1,150 interfaces, over 300 specs), with no hand-picked list. It is organized as webref is, one Lean module per spec, named from the shortname by the mechanical rule (`fetch` → `Lasm.JS.Web.Fetch`, `hr-time` → `HrTime`), all in the namespace `Lasm.JS.Web`, and `import Lasm.JS.Web` imports them all. There are no tiers: `web-tier1.mjs`'s WinterTC list and `web-browser.mjs`'s picks are retired, and **`Lasm.JS.Web.Browser` is removed**. Its users import the spec modules (`import Lasm.JS.Web.Dom`, `import Lasm.JS.Web.Html`). Availability per target moves to build time (0.3-10). Supersedes the tier structure (A51's browser tier and the WinterTC tier 1). Breaking; migration in docs/release/next/web-platform.md. PR #PRNUM, next release. Since then: no umbrella (0.3-18), modules compiled on first import (0.3-6), and a small prebuilt core (the modules the templates and examples import). | decided, pending sign-off |
| 0.3-2 | `Lasm.JS.Web.Browser` (the browser tier) | **Removed** (0.3-1): everything a browser has is web platform, in the spec modules (`Lasm.JS.Web.Dom`, `Html`, `Cssom`, `CssomView`, `Uievents`, …). Lasm.UI.Mount never imported it. Breaking; migration in docs/release/next/web-platform.md. | decided, pending sign-off |
| 0.3-3 | `Lasm.JS.Web.Support` | **Decided: internal.** The helpers the generated code calls are in the namespace `Lasm.JS.Web.Internal` (module `Lasm.JS.Web.Support`), with no stability promise; programs use Lasm.JS directly. `Lasm.JS.Web.Record` stays public, because generated signatures name it. Lasm.JS.Node's own helpers (`Lasm.JS.Node.Support`) are 0.4's to decide. Breaking; migration in docs/release/next/web-platform.md. | decided, pending sign-off |
| 0.3-4 | Generated-binding mapping rules (all tiers) | Overload names (`serve`, `serveWithOptions`), callback type names, number typing, checked downcasts, and the reviewed override table Jordan decided on 2026-11-16: decided in A9–A12 and [BINDING_RULES.md](../../BINDING_RULES.md) (PR #301); the table is `scripts/bindings/overrides.json`. | decided, pending sign-off |
| A9.1 | Lasm.JS.Web, `FormData` | `FormData.appendWithBlobValue` → `FormData.appendBlob`, and `FormData.setWithBlobValue` → `FormData.setBlob`, through the override table. Example: `form.appendBlob "file" blob (some "x.txt")`. Why: the mechanical name repeats the IDL argument name. Rejected: keeping it, or `appendFile`, which is wrong because the spec takes any `Blob`. Breaking; migration in docs/release/next/web-platform.md. PR #301, next release. Detail: [BINDING_RULES.md](../../BINDING_RULES.md#a9-overload-names). | pending sign-off |
| A11.1 | Every tier whose source does not type integers (Node, Deno, Bun, Cloudflare) | The integer table: the rows in `scripts/bindings/overrides.json` `integers`. Each row has a name (or `Owner.name`), `Nat` or `Int`, and a reason. Rows: HTTP `status` and `statusCode`; `port`; sizes and lengths (`size`, `byteLength`, `length`, `keylen`, `outputLength`, `highWaterMark`, `maxBuffer`, `maxmem`, `maxRequestBodySize`); counts (`count`, `limit`, `iterations`, `pendingRequests`, `tcpBacklog`); scrypt's `cost`, `blockSize`, `parallelization`, `N`, `r` and `p`; `fd`, `uid`, `gid`, and `pid` (`Int`); and whole-unit times (`timeout`, `idleTimeout`, `expirationTtl`, `expiration`, `cacheTtl`). Effect today: Node's `crypto.randomBytes`, `pbkdf2`, `hkdf`, `scrypt`, `process.kill`, `FileHandle.fd`, the `child_process` options and the stream options take `Nat`/`Int`. Breaking; migration in docs/release/next/web-platform.md. PR #301, next release. Detail: [BINDING_RULES.md](../../BINDING_RULES.md#a11-numbers). | pending sign-off |
| 0.3-5 | `Request`/`Response` conversion helper | **Decided: none (A13.1).** The generated spec API converts in one call each (`Response.new`, `Response.staticJson`, `req.text`, `req.bytes`, `req.json`); the rest of the 20 lines converts Lasm.Fetch's types, which go with Lasm.Fetch (0.2). | decided, pending sign-off |
| 0.3-6 | Generated binding modules compiled on first import | `Lasm.JS.Web.*`, `Lasm.JS.Node.*`, `Lasm.JS.Deno.*`, `Lasm.JS.Bun.*` and `Lasm.JS.Cloudflare.*`: a module of these namespaces that is not in `libraryModules` ships as source only. The build compiles it into the managed Lean prefix the first time a program imports it, as `lasm editor` does for a project's imports, with the modules it imports, resolved from the sources (src/lazy-library.mjs). It prints `[lasm] Compiling Lasm.JS.Web.IndexedDB (first use)…` and a total, and runs independent modules in parallel (up to half the cores, and one per 3 GB of memory). Outputs are written to a temporary file and renamed. They carry a stamp with their source identity and output hashes, which the tool cache's verification accepts. Why: the whole generated platform is about 300 MB compiled. Committing that to git on every regeneration, and shipping it in npm (483 → ~800 MB), is not acceptable (main, for Jordan, 2026-11-16). This pulls a slice of milestone 3.2 forward for the generated bindings only. No new flags. Rejected: shipping everything prebuilt (size), and a separate cache directory on `LEAN_PATH` (Lean resolves the `Lasm` package from a single root). PR #313. | decided, pending sign-off |
| 0.3-7 | Editor support for modules compiled on first import (Lake projects) | **Decided (main, for Jordan, 2026-11-16; in his sign-off packet as user-facing).** A Lake project's lakefile requires Lasm's library as a Lake package: `[[require]]` with `name = "lasm"` and `path = ".lake/lasm-library"` (lakefile.lean: `require lasm from ".lake" / "lasm-library"`). `lasm init` writes it for the templates that import Lasm's library, and `lasm editor` adds it to an existing project. `.lake/lasm-library` is a link (a junction on Windows) that every lasm command (init, build, dev, editor) makes or repairs, to one package per Lean prefix in Lasm's cache (src/lake-library.mjs): a lakefile whose one library has as roots the modules compiled on first import, from the installed library's sources. Lake builds them on demand, in `lake build` and in the editor's `lake setup-file`. The modules that ship compiled are hard-linked (or copied) into the package's build directory, since Lean takes the package `Lasm` from the first `LEAN_PATH` directory that has `Lasm/`; a receipt records them, and a missing, changed or stale one (an older Lasm, another prefix) is replaced. `lasm build` takes the Lake-built modules' C from Lake and skips its own compile and copy (no double link). Cost: on a fresh clone a plain `lake build` fails until a lasm command has run once (documented in the editor docs and the generated README). Rejected: synthesized Lake traces for the shipped modules (Lake rebuilds an .olean without a real trace), a `lake` wrapper in the editor toolchain (not the platform's own mechanism), and a machine path in the lakefile (not portable). Detail: [GETTING_STARTED.md](../../GETTING_STARTED.md#editor), [HOW_LASM_WORKS.md](../../HOW_LASM_WORKS.md). | decided, pending sign-off |
| A9.2 | Generated bindings, overload names | Overloads with the same argument names and the same number of arguments differ only in their types. Each one after the first adds its argument types: `RTCDataChannel.send` (a string), `sendWithBlob`, `sendWithArrayBuffer`, `sendWithArrayBufferView`. The arity rule (`first0`) stays for overloads with fewer arguments. Why: the earlier rule gave `send1` and `sendWithData`, which say nothing. Rejected: an override entry per case, when the rule is mechanical. PR #PRNUM, next release. Detail: [BINDING_RULES.md](../../BINDING_RULES.md#a9-overload-names). | pending sign-off |
| A13.1 | Lasm.JS.Web | No `Lasm.JS.Web.Convenience`. The ~20 lines per app become calls to the generated spec API: `Response.new (some (.usvString body)) (some { status := some 404, headers := some (.record ⟨#[("content-type", "text/plain")]⟩) })`, `Response.staticJson data`, `(← req.text)`, `(← req.bytes)`, `(← req.json)`, `(← (← req.headers).get "x")`, `URL.new (← req.url)`. Why: the platform's API already says each of these in one call, and a second, Lasm-only shape would have to be learned, documented and kept in step. The rest of the 20 lines converts to and from Lasm.Fetch's types, which go away with Lasm.Fetch (milestone 0.2). Rejected: `Response.text s status` and `Request.bytes` helpers. PR #PRNUM. Detail: [JS_BINDINGS.md](../../JS_BINDINGS.md#standard-bindings-lasmjsweb). | pending sign-off |
| A14.1 | Lasm.UI.Mount | `Mount.signal (α := Value) : IO α`, an `AbortSignal` (`Mount.signal AbortSignal`) of the app. It aborts when the app is unmounted, before the `onUnmount` handlers run, with an `AbortError`. Outside a mounted app it never aborts. Pass it where the platform takes a signal, and the platform removes what it registered: `target.addEventListener "click" (some l) (some (.addEventListenerOptions { signal := some s }))`, `fetch url (some { signal := some s })`, or `s.addEventListener "abort" …` to clear a timer or close a socket. Why: `AbortSignal` is the web's own way to undo registrations, so nothing Lasm-specific is needed (Jordan: do what the platform expects). Rejected: `Mount.track (cleanup : IO Unit)`, which is a second mechanism next to `onUnmount`, and automatic tracking, which would mean wrapping every generated call. Tested in `test/lasm-app.test.mjs` and the platform suite (`app.unmount`, on three engines). PR #PRNUM, next release. Detail: [BROWSER.md](../../BROWSER.md). | pending sign-off |
| A15.1 | Lasm.JS.Web | No batching: `Context2D.draw` and `Event.info` are not brought back. Each generated member is one host call, as the specs define them (cost in [JS_BINDINGS.md](../../JS_BINDINGS.md#cost)). Why: a batch API is a Lasm-only shape over the platform's, and a program that needs fewer calls can write one `@[js]` function in its own JavaScript file (A6). Rejected: generated batch helpers (no spec to generate them from), and hand-written ones (the hand-written `Lasm.Web` was removed for this reason, A51). PR #PRNUM. Detail: [Q15](../SHAPES_REVIEW_2026-11-11.md#4-browser-tier-lasmjswebbrowser-and-lasmuimount). | pending sign-off |
| A16.1 | Lasm.UI.Mount | `subscribe`, `onMessage` and `onUnmount` keep taking plain Lean functions. Why: Mount binds Lasm's own loader (`lasm:app`), not a web API, and nothing registered with it outlives the app (the instance drops its ports and handlers on unmount), so a handle would have nothing to remove. A generated API takes handles because the platform's `removeEventListener` needs the same function back. Rejected: `Port.subscribe (h : PortHandler)`, which adds a step to every use for nothing. PR #PRNUM. Detail: [Q16](../SHAPES_REVIEW_2026-11-11.md#4-browser-tier-lasmjswebbrowser-and-lasmuimount). | pending sign-off |
| 0.3-8 | Lasm.JS.Web layout | One module per spec (`Lasm.JS.Web.Fetch`). Each spec's handle types (the structure and its instances) and enums are in `Lasm.JS.Web.Types.<Spec>`, which imports only its parents' types modules, because the specs name each other's interfaces everywhere (DOM and HTML, Fetch and Streams) and would otherwise merge into one module. A program importing `Lasm.JS.Web.Fetch` builds and links no HTML. A spec's dictionaries, callbacks and typedef'd unions are in that spec's module, and so are the members its partials and mixins add to other specs' interfaces (`Navigator.geolocation` in `Geolocation`; `LinkStyle.sheet` on `HTMLStyleElement` in `Html`, the spec of the `includes`). Specs that still need each other's dictionaries form one module named after them: two today, `WebAnimationsAndWebAnimations2` and `SecurePaymentConfirmationAndWebauthn`. Every dictionary, callback and enum a spec defines is generated, used by a member or not (Streams' `UnderlyingSource`). Rejected: one module (every program would build all of it), and hand-grouped modules (not mechanical). | pending sign-off |
| 0.3-9 | Lasm.JS.Web globals | `Window`'s members, with those of its mixins (`WindowOrWorkerGlobalScope`'s `fetch`, `setTimeout`, `crypto`), are top-level functions on `globalThis` (`document`, `fetch`, `indexedDB`), each in the module of the spec that adds it. They are also methods of a `Window` handle, for another window (`iframe.contentWindow`, `open`'s result). The worker global scopes are interfaces like any other. Why: `Window` is the page's global object, and the mixin's members are the globals of every runtime. Rejected: worker-scope globals at the top level (they collide with Window's: `postMessage`, `name`, `location`). PR #PRNUM. | pending sign-off |
| 0.3-10 | `lasm build --target` | **A build refuses a web API the target lacks.** After Lean compiles the program to C, the build collects the generated `Lasm.JS.Web` bindings it calls, by the full names they pass to `Internal.api` (string literals in the C of the program and of the non-web library modules, 0.3-12) and looks each one up in `library/Lasm/JS/Web/availability.json`, which the generator computes from compatibility data used as it is. `@mdn/browser-compat-data` 8.1.8 covers browsers (Chromium 153, Firefox 155, Safari 26.6, all three), Node 24 and Deno 2.9 (`deno`, `deno-deploy`, `supabase-edge`). unjs/runtime-compat's data, pinned at commit 6136fef9 of 2025-12-01 (the maintained source; its npm package is stale), covers Bun, Workers (workerd), Vercel Edge (edge-light) and Netlify Edge. The function platforms use Node's. The most specific path the data lists decides (`api.Element.append`, then `api.Element`); an unlisted one is unavailable. Error: `Lasm.JS.Web.document (api.Window.document) is not available on --target workers (…). It is available on browsers (…).`, exit 1. There is no flag to skip the check: wrong data is corrected by a reviewed entry of `scripts/bindings/availability-overrides.json`, which has its reason, an upstream report link and its own `0.3-n` record. Rejected: per-target binding surfaces (a program would compile for one target only), and run-time failures (found late, in production). PR #PRNUM. | pending sign-off |
| 0.3-11 | `lasm build --target` | **Open question: feature detection.** A program that deliberately feature-detects (progressive enhancement: use `navigator.share` only where it exists) calls an API its target lacks, and the check (0.3-10) refuses it. Options: (a) a per-declaration attribute in the program (`@[web_optional]`) that turns the check off for that call site's declaration; (b) a typed guard, `Lasm.JS.Web.available? (api : …) : IO Bool` plus a call that is only checked inside the guard; (c) a per-program list of APIs the program detects (`lasm.json` or a Lean `#web_optional` command). Claude recommends (c) as the smallest change: it is explicit, reviewable, and needs no new syntax in call sites. Not built yet. | open |
| 0.3-12 | Lasm.JS.Web, Node, Deno and Bun bindings | Every generated binding is `@[macro_inline]` data with no code of its own: at a call site it expands to the generic Lasm.JS call wrapped in `Internal.api "<full Lean name>"`, which names the binding in errors and lets `lasm build` find a program's web APIs as string literals in its C (0.3-10). Each parameter occurs exactly once in a binding's body (macro_inline substitutes arguments as written), checked by the generator and `test/web-bindings.test.mjs`. Measured: 0.7 KB of olean and no C per binding (2.2 KB and 1.2 KB as a function). Every generated module also sets `genInjectivity false`, `genSizeOfSpec false` and `compiler.extract_closed false`. Stage 2's backend can find the references at the LCNF level instead of in C. Rejected: `@[noinline]` functions (size and speed), and one opaque binding table (not typed). | pending sign-off |
| 0.3-13 | Lasm.JS.Web | `scroll`, `scrollTo`, `scrollBy` and `scrollIntoView` (of `Element` and `Window`) are `Async Unit`: CSSOM View now types them as returning `Promise<ScrollResult>`, which the engines do not return yet. An `Async Unit` awaits either. Listed in `scripts/bindings/web-rules.mjs` (`undefinedPromises`). | pending sign-off |
| 0.3-14 | Lasm.JS.Web | A dictionary that contains itself (Service Workers' `RouterCondition`, through `sequence<RouterCondition> _or`) has `Data` at the member that closes the cycle, because a recursive Lean structure would need recursive conversions. | pending sign-off |
| 0.3-15 | Lasm.JS.Web | Not generated, because the bridge cannot do them: a `[HTMLConstructor]` constructor (it builds only a custom element subclass, which needs A6's classes); unnamed getters, setters and deleters (no method to call); async iteration and `forEach` (use a reader, or `entries`); an iterable of `ArrayBuffer`s (`MediaKeyStatusMap`'s key IDs: each entry would need its own copy; use `get` and `has`). No spec, interface or member is excluded otherwise (`scripts/bindings/web-rules.mjs`). | pending sign-off |
| 0.3-16 | Lasm.JS.Web | A member that two specs both declare (CaptureController's constructor, in Screen Capture and in a spec that extends it) is generated once, from its own interface's spec. | pending sign-off |
| 0.3-17 | Generated enums (Lasm.JS.Web, Node, Deno, Bun) | **Flagged for Jordan; breaking.** A WebIDL enum is `structure E where unsafeOfString :: val : String`, with one `@[match_pattern] abbrev` per value of the pinned IDL (`RequestMode.noCors`). Construction and equality read as before (`.noCors`, `(← res.type) == .basic`), and `match` works, with a final `| _ =>`. A value the pinned IDL lacks (a newer engine's) reads as it is instead of failing. Writes are not checked: `E.unsafeOfString s` makes any value, so the generated values are the normal way. Why: an inductive enum costs about 10 KB per value (a 100-value enum is 1.8 MB of olean, against 0.2 MB now), and the platform's enums grow. `test/web-bindings.test.mjs` checks that every enum's values are exactly the IDL's. Migration: add `| _ =>` to matches on web enums. Rejected: inductives (size, and failing on new values). | pending sign-off |
| 0.3-18 | Lasm.JS.Web | No umbrella module: `import Lasm.JS.Web` is gone. With modules compiled on first import (0.3-6), it would compile every spec (about 300 modules, 5 minutes) on first use. Programs import the spec modules they use. | pending sign-off |
| 0.3-19 | Availability overrides | The first entries of `scripts/bindings/availability-overrides.json`, found by Lasm's own conformance runs: the global `navigator` on Node, Bun and workerd (the data records it under `api.Navigator`); `MessageChannel` on workerd; `File`, `CompressionStream`, `DecompressionStream` and `URLPattern` constructors on Bun 1.4.4 (the data describes Bun 1.3.3); and `WebAssembly.CompileError` everywhere (runtime-compat lists no WebAssembly errors). Each entry has its reason and evidence; upstream reports to runtime-compat follow. | pending sign-off |
