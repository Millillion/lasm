### 0.4-30: documented events are typed listeners

- **Decision:** each stable documented event of a generated class becomes a
  listener type with the event's documented argument types
  (`http.Server.RequestListener`, made with `ofFn` or `ofSyncFn`) and two
  operations, `on<Event>` and `once<Event>`, that call `emitter.on` /
  `emitter.once` with the event's name and return the emitter. Arguments the
  docs give only in prose are stated in `node-tier2.mjs` `eventProse`, quoting
  the sentence. Listener parameters (`requestListener`, `connectListener`)
  take that event's listener type.

  ```lean
  let echo ← http.Server.RequestListener.ofFn fun req res => do
    discard <| res.setHeader "x-method" (← req.method)
    discard <| res.writeHead 200
    discard <| res.«end» (some body)
  let server ← http.createServer none (some echo)
  discard <| child.onceExit (← ChildProcess.ExitListener.ofFn fun code signal => …)
  ```
- **Why:** event names and argument types are part of the documented API; a
  typed listener catches a misspelled event or a wrong argument type at compile
  time. **Alternative:** only the generic `EventEmitter.on (event : String)`
  with `Data` arguments (still available).
- **Where:** #220 (0.9.0), with `node:net`, `node:http` and `node:https`
  (A18: not a serving path; Node servers use `Node.serve`, milestone 0.2).
  **Status:** pending sign-off.

### 0.4-31: parent projections named in full where they collide

- **Decision:** a class whose ancestors' automatic Lean parent projections
  would collide gets the parent's full name (`https.Server.toHttpServer`).
- **Why:** Lean's automatic name (`toServer`) is ambiguous between `net.Server`
  and `http.Server`. **Alternative:** renaming the classes.
- **Where:** #220 (0.9.0). **Status:** pending sign-off.

### 0.4-32: explicit instance names on generated Node types

- **Decision:** instances of generated `Lasm.JS.Node` types have explicit names
  (`instFromJSFsStats`); nothing refers to the automatic ones.
- **Why:** Lean's automatic instance names collided across namespaced types
  (`fs.Stats`, `net.Server`). **Alternative:** none that keeps both types.
- **Where:** #220 (0.9.0). **Status:** pending sign-off.

### 0.4-33: Lasm.JS.Node is every Node core module, generated as the docs give it

- **Decision (Jordan's direction, 2026-11-16: the generated sources as they are):**
  `Lasm.JS.Node` is generated from all 45 documentation files of Node's own
  modules (the table in [JS_BINDINGS.md](../../JS_BINDINGS.md#what-is-covered-1)), one
  Lean module per file, with no hand-picked subset: `node-api.mjs` finds the
  containers itself (every `Class:` section; every module-level owner of
  documented members, `fs`, `fsPromises`, `dnsPromises`, …). The promises,
  callback and synchronous forms of `node:fs` are all generated.

  ```lean
  let gz ← zlib.gzipSync (.domString "hi")
  let back ← zlib.gunzip (.uint8Array gz)          -- Async ByteArray
  let entries ← fs.readdirSync (.domString ".")
  let h ← crypto.createHash "sha256"
  ```
- **Why:** one rule for the whole source; nothing to review per member; users
  get the API Node documents. **Alternatives:** the hand-picked "server
  essentials" of 0.7.0 (retired); `@types/node` (A17).
- **Where:** #317 (0.9.0). **Status:** pending sign-off.

### 0.4-34: stability marks and Node 26 members

- **Decision:** members marked Deprecated, Experimental or Legacy are generated
  and say so in their doc comment (`**Experimental** in the Node.js 24.22.2
  docs`). The bindings follow the Node 24.22.2 docs (the oldest supported Node);
  what only the Node 26.13.0 docs document is added with `**Node.js 26 and
  later**` in its doc comment (`buffer.isLatin1`, `Buffer.stringLength`). The
  conformance run fails on Node when a generated member is missing, except
  Experimental ones and, on Node 24, the Node 26 additions.
- **Why:** the source as it is; a user on Node 26 can use Node 26's API, and
  the marks say where it is not portable. **Alternatives:** stable members only
  (0.7.0's rule); Lean `@[deprecated]` attributes (warnings on every use of a
  deprecated Node API, noisy for members Node keeps working); one binding set
  per Node version.
- **Where:** #317 (0.9.0). **Status:** pending sign-off.

### 0.4-35: web standards stay in Lasm.JS.Web

- **Decision:** a Node class whose name is a web standard interface (`URL`,
  `EventTarget`, `Blob`, `MessagePort`, `TextEncoder`, `PerformanceObserver`,
  …), the `console` namespace, and the members of Node objects that a web
  interface defines (`crypto.randomUUID`, `crypto.getRandomValues`,
  `crypto.subtle`; `performance.now`, `mark`, `measure`, …) are not generated in
  `Lasm.JS.Node`; Node types that name them use `Lasm.JS.Web`'s types.
  Exceptions, Node's own classes that share a web name, are listed
  (`cluster.Worker`, `worker_threads.Worker`, `vm.Module`). **Breaking:**
  `Lasm.JS.Node.crypto.randomUUID` is gone; use `(← Lasm.JS.Web.crypto).randomUUID` (`import Lasm.JS.Web.Webcrypto`).
- **Why:** host namespaces hold only each host's non-web APIs (Jordan,
  2026-11-16); one type per web API across every target. **Alternative:**
  generate Node's own documentation of them too (two types for one object).
- **Where:** #317 (0.9.0). **Status:** pending sign-off.

### 0.4-36: callbacks, overload names and prose types

- **Decision:** a required trailing `callback(err, value)` is `Async value`
  through `util.promisify` (as in 0.7.0); a required callback with more values or
  undocumented arguments is a `JSFunction` argument, as documented; an optional
  trailing callback is left out (its synchronous form). Overloads take the
  shared overload naming (`Buffer.fromWithString`, `Buffer.fromWithArrayBuffer`;
  **breaking:** `Buffer.from` of a string is now `Buffer.fromWithString`, since
  `Buffer.from` has four documented forms). A type the docs give only in prose
  is `any` (`Data`) unless `node-tier2.mjs` `prose` states it with a quoted
  sentence (zlib's convenience methods: `Async ByteArray` and `IO ByteArray`).
  Two classes of one name in different modules are named with their module.
- **Why:** mechanical rules, no per-member choices; a prose statement is the
  docs' own words. **Alternatives:** `util.promisify` for every callback (it
  drops all values but the first, or needs `util.promisify.custom`); failing the
  lowering on prose types (0.7.0, which forced a subset).
- **Where:** #317 (0.9.0). **Status:** pending sign-off; the shared
  rules (A9–A12, docs/BINDING_RULES.md), which landed in 0.9.0 (#301), apply on top.

### 0.4-37: the node-core example and the Node conformance gate

- **Decision:** `examples/node-core` (a file report: `fsPromises`, `crypto`,
  `zlib`, `path`, `os`, `process` only) is built and run by `web-bindings.yml`
  on Node 26 and Node 24, and `test/fixtures/js-node` probes every generated
  member on Node 26, Node 24, Bun and Deno.
- **Why:** every API ships with an example exercised in CI (Jordan's rule).
- **Where:** #317 (0.9.0). **Status:** pending sign-off.

### 0.4-38: what Lasm.JS.Node does not generate, and why

- **Decision:** only what cannot work from Lean compiled to Wasm, or is not a
  named member:
  - `Buffer`'s instance properties (`buf.length`, `buf.buffer`,
    `buf.byteOffset`, `buf.parent`, `buf.poolSize`) and its methods that write
    into the buffer in place without returning it (`buf.write`,
    `buf.writeUInt32BE` and the other `write…` methods): a `Buffer` is a Lean
    `ByteArray`, a copy, so the property describes memory Lean does not hold
    and the write would be lost.
  - Members with computed keys (`buf[index]`, `[Symbol.asyncDispose]()`):
    not named members (`Value.get` with the key reaches them).
  - `inspector.Session`'s `'<inspector-protocol-method>'` event: a placeholder
    for every protocol event.
  - `options.detached`, `options.stdio` in `child_process.md`: spawn's options,
    documented under their own headings (members of `SpawnOptions`).
- **Why:** Jordan, 2026-11-16: exclusions only where something cannot work
  from Wasm, each recorded with its reason. **Alternative:** generating the
  Buffer members against a copy (they would silently do nothing).
- **Where:** #317 (0.9.0); the list is generated into
  `scripts/bindings/node-coverage.json`. **Status:** pending sign-off.

### 0.4-39: no umbrella module, per-module imports, and a compiled core set

- **Decision (main, 2026-11-16, the same rule for every generated host: Web,
  Node, Deno, Bun, Cloudflare):** there is no `Lasm.JS.Node` umbrella module
  and no `Lasm.JS.Node.All`; a program imports each module it uses.
  `library/prebuilt` holds only Node's core set: `node-tier2.mjs` `core`
  (`Events`, `Stream`, `Buffer`, `Path`, `Os`, `Process`, `Fs`, `Crypto`,
  `ChildProcess`) and the modules they import (`AsyncHooks`, `Net`,
  `Readline`), which is what the templates, examples and fixtures use. Every
  other module ships as Lean source and is compiled on first import (0.3-6).

  ```lean
  import Lasm.JS.Node.Fs       -- compiled (core set)
  import Lasm.JS.Node.Http     -- compiled into the tool cache on first use (about 3 s)
  ```
- **Why:** an umbrella forces every module to compile on first use (46
  modules, about 44 s with the macro_inline emitter); one rule across hosts; the packaging decision for
  generated bindings (outputs not committed beyond a small, measured core set).
  **Alternatives:** `import Lasm.JS.Node` as the core set plus
  `Lasm.JS.Node.All` (dropped for consistency with Web and Cloudflare);
  shipping everything compiled (30 MB of `.olean`, 6.3 MB of C with the macro_inline emitter; core set 13.7 MB and 2.8 MB).

### 0.4-11 How TypeScript declarations become Lean (ts-auto rules)

- **Decision:** the rules of [JS_BINDINGS.md, "How Deno's declarations become
  Lean"](../../JS_BINDINGS.md#how-denos-declarations-become-lean), among them:
  an interface with a required method or a `Promise` property, a class, or an
  interface extending one is a handle; plain data is a copied structure; **a
  union of object types is one structure** whose members are optional where an
  alternative lacks them (`KvEntryMaybe`, `KvListSelector`,
  `PermissionDescriptor`, `KvMutation`); other unions are inductives named
  after their alias, else their members (`DOMStringOrURL`), in Lasm.JS.Deno's
  own namespace, with `Coe` from each member (`Deno.readFile "a.txt"`); a
  generic declaration is one type per instantiation (`Conn`, `ConnUnixAddr`;
  an alias's name where one exists: `TcpListener`); a generic method's
  parameter is its default (`unknown` → `Data`); interface properties are
  read-only except function-typed ones (`onchange`); a TypeScript enum is its
  number; `Date` is `Data`; a `symbol` alternative is dropped; an all-capitals
  enum value is a lower-case constructor (`Signal.sigterm`, `.aaaa`).
  ```lean
  let st ← (← Deno.permissions).query { name := .read, path := some (.domString "/tmp") }  -- one structure for 8 descriptor types
  Deno.kill (← Deno.pid) (some (.signal .sigterm))
  let e ← kv.get #["k"] none
  if e.versionstamp.isNone then IO.println "absent"                                    -- KvEntry | {null…} as one structure
  ```
- **Why:** each is what the declaration means for a Lean caller, decided once
  for every Deno (and later Bun) member. A union of object types as one
  structure is what Deno returns (an object that always has the members, some
  null) and what Lean can build and read without a JavaScript discriminant;
  unions in Deno's own namespace keep Lasm.JS.Deno from importing Lasm.JS.Node.
  Alternatives: an inductive per union of objects (rejected: a result cannot be
  told apart by its JavaScript kind, so it would read as `Data`); `Float`-only
  numbers everywhere (kept for now except ports, pending A11).
- **Where:** #307, 0.9.0. Shared rules A9–A12 (0.3), which landed in 0.9.0
  (#301), apply on top.
- **Status:** pending sign-off.

### 0.4-14 Async iterables: values, iterator, next

- **Decision:** a declaration that is or returns an `AsyncIterable<T>`
  (`Deno.readDir`, `Kv.list`, `FsWatcher`, `TcpListener`) has
  `values : Async (Array T)` (every value, to the end) and
  `iterator : IO It` with `It.next : Async (Option T)` (one at a time;
  `none` at the end). An `AsyncIterable<T>` result without its own interface
  is a generated `<T>AsyncIterable` (`DirEntryAsyncIterable`).
  ```lean
  let names := (← (← Deno.readDir (.domString ".")).values).map (·.name)
  let it ← (← Deno.listen {}).iterator
  if let some conn ← it.next then conn.close           -- the first connection
  ```
- **Why:** `for await` is the only way to read these APIs; `values` matches
  Lasm.JS.Web's sync iterables (which collect into an array), and `next` serves
  the endless ones (a listener, a watcher). Alternatives: leave async iteration
  unmapped (as Lasm.JS.Web does; rejected: `readDir`, `Kv.list` and listeners
  would be unusable).
- **Where:** #307, 0.9.0. Lasm.JS.Web's async iterables are unchanged
  (0.3's question).
- **Status:** pending sign-off.

### 0.4-7.3 WebSockets on Node: an npm package bound with `@[js]` (detail of inventory entry 0.4-7; A25)

### 0.4-20 Lasm.JS.Deno and Lasm.JS.Bun ship as source, with no prebuilt core

- **Decision:** no module of `Lasm.JS.Deno` or `Lasm.JS.Bun` is in the prebuilt

  sources ship in `library/` and compile into the managed Lean prefix the first

  `Lasm.JS.Bun` are compiled on first import too: `lazyModules` now finds a
  namespace's umbrella file (`library/Lasm/JS/Deno.lean`) beside its directory.

  small, measured core may be prebuilt, and only for what a template imports. No
  template imports Deno or Bun modules. The examples that do (Conduit, Folio,
  Ledger, Porter, Tandem, deno-kv, bun-sqlite) compile them on their first build.
  Prebuilding all of both namespaces took `library/prebuilt` from 92.6 to 171 MB.

  files (the earlier `Deno.serve` and `Bun.serve` modules) are 2,630,918 bytes, which
  the next regeneration removes. The shipped sources are 227 KB (Deno, and
  Bun's serve module) and about 1.1 MB once #312 adds the rest of Bun.

  templates use; the rest of both namespaces still compiles on first import.
- **Checked by:** `test/web-bindings.test.mjs` (no Deno or Bun module prebuilt

  lowering gave every namespace of a section its bare properties (`process.hrtime.arch`); a bare property now belongs
  to the section's own object, and `process.features` is reparented (0.4-44). Namespaces that are exports of

### 0.4-45 and 0.4-46: SQL NULL, rest parameters and documented constructors

Found while moving the apps' hand-written SQLite onto the generated bindings (0.5 and 0.4 app work, 2026-11-17).

- **0.4-45.** Node documents `statement.all([namedParameters][, ...anonymousParameters])` with
  `anonymousParameters {null|number|bigint|…}`; the lowering dropped the `null` of a rest parameter's elements, so
  SQL NULL could not be bound. A rest parameter now keeps it (`Array (Option …)`, `none` is `null`). The leading
  optional `namedParameters` was passed as `undefined` ahead of the positional values (which Node then tries to bind):
  optional parameters before a rest parameter now give two functions, as optional parameters before a required one
  already did.

  ```lean
  let ins ← db.prepare "insert into t (a, b) values (?, ?)"
  discard <| ins.run #[none, some (.double 7)]          -- a NULL, b 7
  let rows ← (← db.prepare "select * from t where a is ?").all #[none]
  ```

  Bun's `Statement.all(...params: ParamsType)` with `ParamsType extends SQLQueryBindings[]` was read as an array of
  arrays (each value wrapped in its own array); the rest parameter's element type is now read through the type
  parameter's bound: `stmt.all #[.null, toJS 7]`.
- **0.4-46.** The docs' JSON keeps a constructor's parameters as the class's `signatures` but loses its heading, so
  only the 10 constructors stated in `node-tier2.mjs` were generated (`DatabaseSync`, `stream.Writable`, `Hash`
  had none). The lowering now reads the constructor headings of the Markdown source at the same tag
  (`### \`new DatabaseSync(path[, options])\``), pinned in `node-api.lock.json` like the JSON: 38 constructors.
  **Alternative:** stating each constructor by hand (the 0.7.0 approach, which does not scale to every class).
- Also fixed: zlib's convenience methods (`zlib.gzip`, `gzipSync`, …) were dropped from the Node 24 lowering
  (the JSON lists them twice, and the prose check read the wrong section), so they had been generated from the
  Node 26 docs and marked "Node.js 26 and later".

**Where:** #352 (0.10.0). **Status:** pending sign-off.
