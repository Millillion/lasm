## Milestone 0.2 decisions, in detail

Decided by Claude on 2026-11-16 under Jordan's rules (platform-native shapes;
Node servers use `Node.serve`, shaped like `Bun.serve`; function platforms use
`exportDefault`, called directly by the generated platform file). Every entry
here is **pending sign-off**.

### A19: `Node.serve`'s options (#222)

**Decision.** `Lasm.JS.Node.serve : ServeOptions → IO Unit`, in the module
`Lasm.JS.Node.Serve`, hand-written (not generated, not a Node API) on the
builtin module `lasm:node-serve` (`node:http`, no npm package).

```lean
import Lasm.JS.Node.Serve
open Lasm.JS Lasm.JS.Web

def handle (request : Request) : Async Response := do
  Response.new (some (.usvString s!"{← request.method} {← request.url}")) none

def main : IO Unit := Node.serve { fetch := handle, port := some 3000 }
```

```lean
structure ServeOptions where
  fetch : Request → Async Response                     -- a plain Lean function
  port : Option Nat := none                            -- $PORT, else 3000 (Bun)
  hostname : Option String := none                     -- "0.0.0.0" (Bun)
  signal : Option AbortSignal := none                  -- Deno.serve's
  onListen : Option (Server → IO Unit) := none         -- Deno.serve's
  error : Option (IO.Error → Async Response) := none   -- Bun's
structure Server where hostname : String; port : Nat; url : String; val : Value
def Server.stop (server : Server) (closeActiveConnections := false) : Async Unit  -- Bun's
def Server.finished (server : Server) : Async Unit                                  -- Deno's
```

- **Options kept:** `onListen` and `signal` (Deno's names; Bun has none), and
  a graceful stop on SIGTERM and SIGINT (requests in progress finish; a second
  signal closes them), as Lasm.Fetch's Node server did, because containers and
  process managers stop servers with SIGTERM.
- **Not added:** a request body size limit (`maxRequestBodySize` in Bun).
  Node's `node:http` has none either; a handler that needs one reads the body
  as a stream. It can be added later under Bun's name without breaking.
- **Why:** Jordan's direction (2026-11-11): one options record with `fetch`
  inside, Bun's names where Bun has the option.
- **Alternatives:** `@hono/node-server` bound in each program (the 0.7.0
  path); a `NodeServer.lean` copied by `lasm init` (PR #212's candidate);
  serving with the generated `node:http` by hand (about 25 lines buffered,
  100–150 production-grade, per #220).
- **Where:** PR #222; release: the next one after 0.8.0.

**A19.1: `Node.serve` blocks until the server stops.** Bun's `serve` returns
the `Server` at once. Lean's runtime ends when `main` returns (it finalizes
its task manager and exits), so a returning `serve` would make every program
end with `server.finished.block`. The blocking form keeps the one-line
`def main := Node.serve { fetch := handle }`; the handle reaches the program
through `onListen`. Alternative: Bun's non-blocking `serve : ServeOptions →
IO Server`.

**A19.2: names.** Bun's `error`, not `onError`; `Server.url` is a `String`,
not Bun's `URL`; `$HOST` is not read (Bun reads only `$PORT`, and binds every
IPv4 address).

### A20: Lasm's Node entry does not serve `exportDefault` (#222)

**Decision: no.** On Node, `exportDefault` only records the value; a program
that serves HTTP on Node calls `Node.serve`. Deno and Bun serve a module's
`export default { fetch }` natively (`deno serve`, `bun run`), so Lasm's Deno
and Bun entries keep doing that. Node has no such convention, and serving a
default export on `$PORT` there would be Lasm-specific behavior that depends
on how the program was started, which Jordan's rules exclude.
**Alternative:** serve `exportDefault` on `$PORT` on Node too, so one program
runs everywhere (the review's earlier recommendation).

### A21: a typed `exportDefault`; no plain-function wrappers for Bun and Deno (#222)

**Decision: option (b).** `exportDefault` takes a Lean fetch handler directly:

```lean
class DefaultExport (α : Type) where toDefaultExport : α → IO Data
instance (priority := low) [ToJS α] : DefaultExport α     -- a Hono app (`Value`), `{ fetch }`, a handler structure
instance [FromJS α] [ToJS β] : DefaultExport (α → Async β)      -- Function.ofFn1
def Lasm.JS.exportDefault [DefaultExport α] (x : α) : IO Unit

def main : IO Unit := exportDefault handle   -- handle : Request → Async Response
```

`Lasm.JS.Bun` and `Lasm.JS.Deno` keep their generated shapes
(`Bun.ServeOptionsFetch.ofFn`, `Deno.ServeHandler.ofFn`): they are the
runtimes' own APIs, and a Lasm wrapper beside them would be a second way to
do the same thing. **Alternatives:** (a) also plain-function `serve` wrappers
for Bun and Deno; (c) keep `exportDefault (← Function.ofFn1 handle)`.

**A21.1: handlers that need the platform's context.** The function form gets
only the request. Workers' `env` and `ctx` and Netlify's `context` go through
the `Value` form today; the typed Workers `env` (a program's `structure Env`
with `deriving FromJS`) is milestone 0.5's (A26).

### A7: `exportDefault`'s argument (#222, combining #216's `[ToJS α]`)

**Decision:** the class `DefaultExport`, whose instances are every type with
`ToJS` (#216's decision, 0.5.md: a `Value`, or a structure of handlers such as
`Lasm.JS.Cloudflare.ExportedHandler`) and, in addition, a Lean fetch handler
`α → Async β`, published as a JavaScript function through `Function.ofFn1`:

```lean
class DefaultExport (α : Type) where toDefaultExport : α → IO Data
instance (priority := low) [ToJS α] : DefaultExport α
instance [FromJS α] [ToJS β] : DefaultExport (α → Async β)
def exportDefault [DefaultExport α] (x : α) : IO Unit
```

`ToJS` of a Lean function is not defined (a function needs `Function.ofFn1`,
an `IO` step), so `[ToJS α]` alone cannot take a handler. **Alternative:**
a `ToJS` instance for functions, which would hide an allocation in a pure
conversion.

### A22: `Node.serve` lives in `Lasm.JS.Node`, module `Lasm.JS.Node.Serve` (#222)

**Decision:** the namespace `Lasm.JS.Node` (so `open Lasm.JS` gives
`Node.serve`, as `Bun.serve` and `Deno.serve`), in its own module
`Lasm.JS.Node.Serve`, imported explicitly: the generated `import
Lasm.JS.Node` does not include it. The generated `node:http` binding (#220)
names its classes `http.Server` and `net.Server`, so `Node.Server` and
`Node.ServeOptions` do not collide. **Alternative:** `Lasm.JS.Serve.node`,
which separates hand-written from generated code but reads unlike
`Bun.serve`.

### A23: `Lasm.Serverless` is deleted; its useful proofs move to the test suite (Jordan, 2026-11-16)

**Decision (Jordan's):** once each function platform's generated file calls
the `exportDefault` handler directly (this PR), `Lasm.Serverless` is deleted
from the library. It has no runtime API: it is a Lean model of the shims
(`lasm-function.mjs`, formerly `lasm-server.mjs`, and `lasm-lambda.mjs`) and
20 propositions about them. The model and the propositions that still
describe the generated platform files (each event becomes one `Request`;
one plain Host; one Cookie field; the reply's status, fields and body reach
each platform's response) move into the test suite, beside the other models
of the CLI's JavaScript (`verification/`), where the serverless-http fuzz
oracle keeps running the model on every input. Propositions about the
loopback forwarding (the target `http.request` sends) are dropped with it.
This PR only restates the model for the direct call; the move is milestone
0.2's own follow-up PR (entry 0.2-7). **Alternatives:** keep the proofs in
the library (they describe CLI code, not a library API); drop them all.

### 0.2-6: the function-platform shims call the handler directly (#222)

**Decision:** `lasm package` and `lasm build --target
netlify|vercel|lambda|lambda-edge|azure|gcf` generate a file that calls
the program's `exportDefault` handler in-process (Netlify `export default
async (request, context)`, Vercel and GCF `(req, res)`, Lambda events, Azure
`HttpResponseInit`). There is no HTTP server, port or loopback. Under that
file, `exportDefault` hands the handler to the platform file and does not
return, because the Lean runtime ends with `main`. A program that brings its
own server (Express, Fastify, `Std.Http`, `Node.serve`) does not run on the
function platforms (the Lambda container image calls the handler too; 0.2-11).
**Alternative:** keep the
loopback adapter (`lasm-server.mjs`), which Jordan rejected on 2026-11-11.

### 0.2-7: `Lasm.Serverless` leaves the library

**Decision (Jordan's, A23):** the library namespace `Lasm.Serverless` (a model
of the function-platform files, with 20 proved propositions and one
candidate, and no runtime API) is no longer part of Lasm's library. Its files
move unchanged to `verification/cli/Lasm/Serverless/`, beside the other models
of the CLI's JavaScript: `scripts/library-proofs.mjs` still compiles and
checks them, `verification/cli/README.md` lists their propositions (not
`library/PROOFS.md`), and the serverless-http fuzz oracle still runs the model
on every input. All 20 propositions still describe `lasm-function.mjs` and
`lasm-lambda.mjs` (the request target and fields each event becomes, and the
response each platform gets), so none is dropped. The Lean names stay
`Lasm.Serverless.*`, so the tests' `Proposition:` citations are unchanged.
**Where:** PR "Lasm.Serverless moves to verification/cli".

### 0.2-4: templates serve with one entry module per serving model (no `onEdge` branch)

**Decision.** `lasm init --template fetch` and `--template hono` write the
handler once and one small program per way of serving it, with no
`Lasm.JS.onEdge` branch:

| File | fetch | hono | Built by |
| --- | --- | --- | --- |
| `Handler.lean` / `Routes.lean` | `Handler.handle : Request → Async Response` | `Routes.app : IO Value` (the Hono app) | (imported) |
| `Main.lean` | `Node.serve { fetch := Handler.handle }` | `@hono/node-server`'s `serve`, Hono's own Node adapter | `npm run build`, `dev`, `start`, the Dockerfile |
| `Export.lean` | `exportDefault Handler.handle` | `do exportDefault (← Routes.app)` | `build:bun`, `build:deno`, every edge and function-platform `build:<target>` |
| `Fastly.lean`, `WasiHttp.lean` | the same routes on `Lasm.Fastly` and `Lasm.WASI.Http` (unchanged) | – | `build:fastly`, `build:wasi-http` |

```lean
-- Main.lean (fetch)
import Handler
import Lasm.JS.Node.Serve
open Lasm.JS
def main : IO Unit := Node.serve { fetch := Handler.handle }

-- Export.lean (fetch)
import Handler
import Lasm.JS
open Lasm.JS
def main : IO Unit := exportDefault Handler.handle
```

**Why:** each platform gets what it natively expects (a server on Node, a
default export elsewhere), and no program changes behavior with where it
runs. **Alternatives:** one `Main.lean` that branches on `onEdge` (0.8.0's
templates; context-dependent); `Main.lean` as the default export and a
separate `Node.lean` (the Node build is the default one, so it keeps the
name `Main.lean`). **Where:** this PR. Supersedes A53.

### 0.2-10: the function platforms take the templates that publish a handler

**Decision.** `--deploy lambda|lambda-container|lambda-edge|vercel|netlify|azure|gcf`
accept the hono and fetch templates only (they build `Export.lean`). The
express, fastify and std-http templates bring their own server, so they have
no function-platform target: they run on container platforms (the
`Dockerfile`); `lasm init` refuses the others with the targets the template
supports. **Alternatives:** port express and fastify to a handler (they are
Node servers by design); keep a loopback adapter (rejected by Jordan,
2026-11-11). **Where:** this PR.

### 0.2-11: the Lambda container image calls the handler; no Web Adapter

**Decision.** `--deploy lambda-container` writes a `Dockerfile.lambda` whose image is
Lambda's own Node 24 base image with the .zip package's files (`lasm build
Export.lean --target lambda`, unzipped) and `CMD ["lasm-lambda.handler"]`:
the base image's runtime interface client calls the handler, which calls the
program's `exportDefault` handler. No HTTP server runs inside the function.

```dockerfile
FROM public.ecr.aws/lambda/nodejs:24
COPY --from=build /lambda ${LAMBDA_TASK_ROOT}/
CMD ["lasm-lambda.handler"]
```

**Why:** the AWS Lambda Web Adapter forwards each invocation to a server on a
port inside the function: a loopback adapter, which Jordan's rule excludes.
The base image with a handler is AWS's documented container form for Node.
**Consequence:** express, fastify and std-http lose `--deploy lambda-container` (they
cannot publish a handler). **Alternatives:** keep the Web Adapter image for
the server templates. **Where:** this PR.

### A44 and 0.2-9: the WASI CGI server mode is dropped (Jordan, 2026-11-16)

**Decision:** HTTP on WASI goes through wasi-http only. `--target wasi`
stays for command-line and batch programs. `lasm init --template fetch` no
longer accepts `--deploy wasi` and has no `Cgi.lean`; `--deploy wasi` is the
plain template's. The CGI glue and its fuzz target go with `Lasm.Fetch`
(0.2's deletion PR). **Alternatives:** CGI as template-only code (0.8.0) or a
small library.

### A41–A43: no new namespaces replace Lasm.Fetch's helpers (Jordan, 2026-11-16)

- **A41, embedded assets:** apps embed their own (Conduit's and Folio's
  `Server/Embed.lean` and `Server/Assets.lean`, the fullstack template's
  `Embed.lean`). No `Lasm.Embed`.
- **A42, request and routing helpers:** apps route in a few lines of pure
  Lean; on JavaScript hosts they read the URL with `Lasm.JS.Web`'s `URL` and
  `URLSearchParams`, as the templates do. No `Lasm.Http.Path`.
- **A43, outbound requests:** each host's own API: `Lasm.JS.Web.fetch` on
  JavaScript, `OutgoingHandler.handle` on wasi-http, `HttpReq.send` on
  Fastly. No cross-host `send`.

**Why:** Jordan's direction (2026-11-16): no Lasm-specific layer between a
program and its host. **Alternatives:** the review's options (b) and (c) for
each (a small transport-free library, or a CLI feature).

### 0.2-12: the fullstack template speaks plain REST (routes agreed with 0.6 through main, 2026-11-16)

**Decision.** `lasm init --template fullstack` drops `Lasm.RPC` and
`Lasm.Fetch`. `Shared.lean` holds the types (`Todo`, `NewTodo`, `TodoPatch`,
`ApiError`), the check and its theorem, and `ValidTitle := { title : String //
checkTitle title = .ok () }`; `Site.lean` routes:

| Request | Answer |
| --- | --- |
| `GET /api/todos` | 200, `[Todo]` |
| `POST /api/todos` `{"title"}` | 201, `Todo`; 400 `{"error"}` when the title fails the check or the body is not JSON |
| `PATCH /api/todos/ID` `{"done"}` | 200, `Todo`; 404 `{"error"}` |
| `DELETE /api/todos/ID` | 204; 404 `{"error"}` |

```lean
-- Site.lean
def Store.add (s : Store) (title : ValidTitle) : Store × Todo := …
```

The server programs follow the fetch template (0.2-4): `Server.lean` on Node
(`Node.serve`), `Export.lean` for the edge, Bun and Deno (`exportDefault`),
`Fastly.lean` and `WasiHttp.lean` (on `Lasm.WASI.Http.respond`); HTTP as plain

### 0.2-13: the fullstack template keeps its todos in each platform's own store, declared, never a silent fallback

**Decision.** The template drops `Lasm.KV` (milestone 0.5 deletes it). `Site.lean`
takes a two-function store, `Site.Kv` (`get`, `put`, and `Kv.memory`), and each
server program gives it its platform's own:

```lean
-- Workers.lean (npm run build:workers); wrangler.toml binds TODOS
structure Env where
  TODOS : KVNamespace
  deriving FromJS

def store (ns : KVNamespace) : Site.Kv where
  get key := ns.get key
  put key value := ns.put key (.domString value)

def main : IO Unit := do
  exportDefault (← ExportedHandlerFetchHandler.ofFn fun request (env : Env) _ctx =>
    JsSite.handle (store env.TODOS) request)
```

`Deno.lean` (deno, deno-deploy) keeps them in Deno KV through the generated
`Lasm.JS.Deno.Kv` (`openKv`, `Kv.get`, `Kv.set`; keys `["TODOS", key]`, opened
on the first request) and fails at start when Deno KV is absent; `Fastly.lean`
uses the KV Store `TODOS` through `Lasm.Fastly.KvStore` and fails a request
when the store is absent; `Server.lean` (Node), `Export.lean` (Bun, Vercel
Edge, Netlify Edge) and `WasiHttp.lean` keep them in memory, as before.
`wrangler.toml` now declares the `TODOS` binding.

**Why:** #331's `Export.lean` opened `Lasm.KV.open "TODOS"`, whose Workers
lookup read `Lasm.Fetch.platformEnv`, which only Lasm.Fetch's server set: on
Workers every read and write silently went to the isolate's memory (fullstack.yml
run 44101854124, kv-across-restart). The typed `Env` (A26) makes a missing
binding an error that names it. **Alternatives:** set
`Lasm.Fetch.platformEnv` from the handler (keeps a library 0.2 deletes);
`Lasm.JS.Cloudflare.env` at start instead of the handler's `env`.
**CI:** fullstack.yml's Workers, Bun/Deno and Fastly/wasi-http jobs, with
their restart checks, now run on pull requests that touch the template.
