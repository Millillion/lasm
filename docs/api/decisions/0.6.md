## 0.6 decisions: the `Lasm.*` libraries

Decisions of ROADMAP.md's milestone 0.6, each with its shape, code, why, the
alternatives, and where it shipped. They decide the inventory's 0.6 entries
above (by their id) and the questions A1–A56; new entries continue from 0.6-20.

### Lasm.WASI.Http and Lasm.Fastly (host bindings)

#### A30: the WASI mapping rules confirmed

**Decision.** Lasm.WASI.Http keeps the mapping of 0.7.0 (#202), the one
wit-bindgen gives every language with typed results:

- `result<T, E>` is `Except E T` inside `IO`; an `IO.Error` means only "not a
  wasi-http host".
- A resource is `structure R where handle : UInt32`, dropped explicitly with
  `R.drop`; ownership is the WIT's (`own` moves, `borrow` lends).
- Names follow heck, as wit-bindgen does; methods take `self`, so dot
  notation works (`request.method`, `Fields.fromList`).
- The export is `IncomingHandler.serve (handler : IncomingRequest → ResponseOutparam → IO Unit)`,
  one instance per request.

```lean
def main : IO Unit := IncomingHandler.serve fun request out => do
  match ← request.consume with          -- IO (Except Unit IncomingBody)
  | .ok body => …
  | .error () => …
```

**Why.** These are the WIT's own semantics: its errors are values a program
handles, and resources have explicit lifetimes the host tracks. Rust's, C's
and Go's wit-bindgen output read the same way.

**Alternatives.** Throwing the WIT errors as `IO.Error` (loses their type);
freeing resources through Lean's reference counting (a handle's drop order
matters to the host: a stream before its body); renaming toward Lasm.JS.Web's
names (wasi:http is not the fetch API).

**Where.** 0.7.0 (#202), unchanged. Full rules: docs/WASI_FASTLY_BINDINGS.md,
"Mapping rules". **Status:** pending sign-off.

#### A31: hand-written helpers for whole bodies, and `respond`

**Decision.** A small hand-written module, `Lasm.WASI.Http.Respond`, imported
by `Lasm.WASI.Http`:

```lean
InputStream.readAll (s : InputStream) : IO (Except StreamError ByteArray)
OutputStream.writeAll (s : OutputStream) (bytes : ByteArray) : IO (Except StreamError Unit)
IncomingRequest.readBody (request : IncomingRequest) : IO ByteArray
respond (out : ResponseOutparam) (status : UInt16) (headers : Array (String × String)) (body : ByteArray) : IO Unit

def main : IO Unit := IncomingHandler.serve fun request out => do
  let body ← request.readBody
  respond out 200 #[("content-type", "text/plain")] s!"{body.size} bytes\n".toUTF8
```

**Why.** Every wasi:http program wrote these (the `fetch` template, Conduit
and examples/wasi-http each had a copy): `blocking-write-and-flush`
takes at most 4,096 bytes per call, and a body is a resource whose stream is
dropped before it is finished. The two stream helpers keep the WIT's error
values, as the calls they repeat do; `readBody` and `respond` make several
calls and throw an `IO.Error` naming the one that failed. `respond` checks
every header before the response is set, so a refused header sends nothing.
Streaming, trailers and outgoing requests stay on the generated calls.

**Alternatives.** Keeping it per app (Q31): the same 60 lines everywhere. A
whole `Request`/`Response` layer over wasi:http: that is what Lasm.Fetch was,
and Stage 0 removes it.

**Tests.** examples/wasi-http uses all four, under `wasmtime serve` in
wasi.yml. Docs: docs/WASI_FASTLY_BINDINGS.md, "Helpers".

**Where.** PR (this one), next release. **Status:** pending sign-off.

#### A32: Fastly errors stay `EIO FastlyStatus α`

**Decision.** Every Lasm.Fastly call stays an `EIO FastlyStatus α` action,
lifting into `IO` with the message `Fastly host call failed: <status>`;
`found?` maps `$none` to `Option.none`.

```lean
let agent ← found? (HttpReq.headerValueGet req "user-agent")    -- Option String
match ← (ConfigStore.get settings "color").toBaseIO with
| .ok color => …
| .error .none => …                                               -- a typed status
```

**Why.** The witx's every function returns `(expected T (error $fastly_status))`.
`EIO ε` is Lean's own typed-error `IO`: a program that does not care writes
plain `IO`, one that does matches the status. **Alternatives.** `IO α` with
the status only in the message (untyped); `IO (Except FastlyStatus α)`
everywhere (every call site unwraps).

**Where.** 0.7.0 (#194), unchanged. **Status:** pending sign-off.

#### A33: `send_v2`/`send_v3` stay unbound for now

**Decision.** The five functions that report a `$send_error_detail`
(`send_v2`, `send_v3`, `pending_req_poll_v2`, `pending_req_wait_v2`,
`pending_req_select_v2`) stay unbound; `HttpReq.send` and the v1
`pending_req_*` cover sending, and fail with the status alone.

**Why.** Binding them needs a second error type, `EIO (FastlyStatus × SendErrorDetail) α`,
and a generator rule for output records, for a detail (DNS, TLS or connection
error) that no Lasm app reads yet. They are listed with the reason in
scripts/bindings/fastly-surface.json. The trigger to bind them is the first
program that must tell a DNS failure from a refused connection.

**Alternatives.** Bind them now with the pair error type (Q33): a second
error type in one API before anyone needs it.

**Where.** 0.7.0 (#194), unchanged. **Status:** pending sign-off.

#### A34: Fastly keeps the witx layout, without dot-notation aliases

**Decision.** Fastly calls stay in one namespace per witx module, with the
witx's names: `HttpReq.methodGet req`, `KvStore.lookupWaitV2`. No aliases on
the handle types.

```lean
let method ← HttpReq.methodGet req
HttpResp.statusSet resp 200
```

**Why.** In witx a handle is a bare `(handle)` type, not a resource with
methods; the functions belong to modules (`fastly_http_req.method_get`). The
Lean names are those, one to one, so the ABI's documentation reads directly.
WASI's dot notation (A30) comes from WIT resources, which witx does not have.
Aliases would give every call two names.

**Alternatives.** Generated aliases (`req.methodGet`): a second spelling of
244 functions; renaming to methods on handles: departs from the ABI.

**Where.** 0.7.0 (#194), unchanged. **Status:** pending sign-off.

### Lasm.UI

#### 0.6-8: Lasm.UI is cut to its core (Jordan, 2026-11-16)

**Decision.** Lasm.UI keeps what only a UI framework can do: `Html` and
`html!`, the proved diff and applier, the app loop (`init`, `update`, `view`,
`subscriptions`), events and decoders, URL changes and routing, SSR and
hydration. Its own wrappers of browser APIs are removed. The app loop's own
effects stay data; everything else is one generic command over the generated
browser bindings:

```lean
inductive Effect (Msg : Type) where
  | msg (msg : Msg)
  | delay (ms : Nat) (msg : Msg)
  | navigate (url : String) (replace : Bool)        -- Cmd.pushUrl / replaceUrl
  | task (run : (Msg → IO Unit) → Async Unit)

def Cmd.task (run : Async Msg) : Cmd Msg
def afterFrame : Async Unit                          -- the next frame is on screen

| .load, m => ({ m with loading := true }, Cmd.task do
    let r ← Lasm.JS.Web.fetch (.usvString "/api/items")
    return .loaded (← r.text))
```

Removed: `Http` (`Request`, `Response`, `Error`, `get`, `post`, `request`),
`Storage`, and the commands `now`, `randomBytes`, `randomNat`, `back`,
`forward`, `load`, `storageSet`/`Get`/`Remove`, `focus`, `blur`, `title`,
`port` and `io`, with their `lasm:ui-dom` exports. Each is a few lines of
`Cmd.task` over `Lasm.JS.Web.Browser` (`fetch`, `localStorage`,
`crypto.getRandomValues`, `history.go`, `location.assign`, `document.title`),
or `Mount.port` for ports. The migration table is in docs/release/next-notes.md.

`Cmd.task` takes the platform's own shape for a browser action, an `Async`
computation (the web's promise-returning APIs, awaited without holding a
thread), and delivers the message it returns. Its effect is in
continuation form, `(Msg → IO Unit) → Async Unit`, so one action can deliver
no message, one, or a stream, and `Cmd.map` stays definitional: the proved
`cmd_map_comp`, `cmd_map_id`, `cmd_map_effects` and `cmd_map_batch` keep their
proofs unchanged. `Cmd.pushUrl` and `replaceUrl` stay because routing is the
loop's: they make the history entry with the frame that shows the new page and
run `onUrlChange`, which a bare `history.pushState` would not. `afterFrame`
stays because only the loop knows when its frame is on screen (focusing an
element the update just added).

Apps that want effects they can inspect in tests and proofs declare their own
effect data and interpret it with `Cmd.task` (docs/UI.md, "Effects you can
test"); examples/ui/todomvc does, and proves what its `update` saves
(`Todo.update_saves`).

**Alternatives.** Keeping UI's wrappers as pure data (A35's recommendation
before this decision): a second, smaller copy of the web platform to keep
current. `Cmd.task : Async Msg → Cmd Msg` alone, without the continuation
form: `Cmd.map` would need the functor laws of `Async`, which Std does not
provide, and streams would need another effect.

**Tests.** The proofs above (library-proofs.yml); test/ui/DocsTest.lean (the
guide's examples); examples/ui/demo (HTTP, focus and ports through
`Cmd.task`) and examples/ui/todomvc (storage and focus) in the browser suite
(ui.yml); test/ui-dom.test.mjs (`afterFrame`).

**Where.** PR (this one), next release (breaking). The example apps pinned
to a published `@lasm/cli` (Conduit, Ledger, Tandem, Porter, Folio) move to
`Cmd.task` with the version bump that moves their pins. **Status:** pending
sign-off.

#### A35: UI's own `Http`, `Url` and `Storage`

**Decision.** `Http` and `Storage` are removed (0.6-8): the generated
`fetch` and `localStorage` replace them through `Cmd.task`. `Url` stays: it is
the type `onUrlChange` and `init` hand the app, pure data that routing code
matches on and proofs reason about (`Url.parse`, `segments`, `param?`,
`Url.build`).

```lean
def route (u : Url) : Page :=
  match u.segments with
  | ["items", id] => .item id.toNat!
  | _ => .home
```

**Why.** `Url` is the app loop's routing input, not a wrapper of a browser
call. **Alternatives.** Lasm.JS.Web's `URL` for routing: a handle, so a pure
`view` and `route` could not use it, nor a proof.

**Where.** PR (this one). **Status:** pending sign-off.

#### A36: the `_` suffix names stay

**Decision.** Names that clash with Lean keywords or core names keep a
trailing underscore: `class_`, `main_`, `id_`, `type_`, `for_`, `section_`.
`html!` uses the plain HTML names (`<main class="…">`), so only the function
DSL sees the suffix.

```lean
main_ [class_ "app"] [section_ [] [text "…"]]
html! <main class="app"><section>…</section></main>
```

**Why.** It is the common convention in Lean and the Elm-family libraries
(Elm's `Html.Attributes.class` needs no suffix only because Elm has no
`class` keyword). «guillemets» (`«class»`) are Lean's escape for an
identifier, not meant for everyday calls, and they are hard to type.

**Alternatives.** «guillemets»; a prefix (`hClass`); a namespace per kind
(`Attr.class`, still a keyword clash).

**Where.** Unchanged since Lasm.UI shipped. **Status:** pending sign-off.

#### A56.1: Lasm.UI stays in `@lasm/cli` for now (Jordan, 2026-11-16)

**Decision.** Lasm.UI keeps its name and ships inside the core package,
`@lasm/cli`, compiled into the managed Lean prefix with Lasm.JS
(`import Lasm.UI`). There is no separate `@lasm/ui` package for now; A56,
where the libraries live, is otherwise still open.

**Why.** Jordan's call: the split adds a resolution mechanism and a release
artifact before anyone needs Lasm.UI without the CLI. Lasm.UI already uses
only public Lasm.JS APIs plus its builtin `lasm:ui-dom` module, so a later
split stays mechanical (with A6.1's project files carrying the applier).

**Where.** Decided 2026-11-16. **Status:** pending sign-off.

#### 0.6-8 (continued): `Url.percentDecode` returns `Option String`

**Decision.** `Lasm.UI.Url.percentDecode : String → Option String` keeps its
`Option`: `none` when the escapes do not decode to UTF-8 (`%FF`), so routing
code sees a malformed URL instead of a guess. `Lasm.Fetch.percentDecode`, which
returned the input unchanged instead, is deleted with Lasm.Fetch (0.2), so the
inconsistency the inventory noted goes with it.

```lean
#guard Url.percentDecode "caf%C3%A9" == some "café"
#guard Url.percentDecode "%FF" == none
```

#### 0.6-9: `html!`'s helper terms stay

**Decision.** `html!` expands `{t}` to `lasm_children% t` (children) and
`lasm_attrs% t` (attributes), two term elaborators that fit `t` to a list by
its type, so the message type flows from the context into nested `html!` and
lambdas. They stay public syntax: a macro can only expand to syntax that
parses, and Lean's own elaboration helpers work the same way (`binop%`,
`unop%`, `leftact%`). Their names say they are Lasm's; nobody writes them.

**Alternatives.** Type classes (`ToChildren α Msg`) instead of the elaborator:
the message type would no longer flow into lambdas inside `{…}`, and the
error messages would be about instances, not the markup.

**Where.** Unchanged since `html!` shipped. **Status:** pending sign-off.
