## 0.6 decisions: the `Lasm.*` libraries

Decisions of ROADMAP.md's milestone 0.6, each with its shape, code, why, the
alternatives, and where it shipped. They decide the inventory's 0.6 entries
above (by their id) and the questions A1–A56; new entries continue from 0.6-20.

### Lasm.WASI.Http and Lasm.Fastly (host bindings)

#### A30: the WASI mapping rules confirmed

**Decision.** Lasm.WASI.Http keeps the mapping of 0.7.0 (#202), the one
wit-bindgen gives every language with typed results:

- `result<T, E>` is `Except E T` inside `IO`; an `IO.Error` means only "not a
  wasi-http host".
- A resource is `structure R where handle : UInt32`, dropped explicitly with
  `R.drop`; ownership is the WIT's (`own` moves, `borrow` lends).
- Names follow heck, as wit-bindgen does; methods take `self`, so dot
  notation works (`request.method`, `Fields.fromList`).
- The export is `IncomingHandler.serve (handler : IncomingRequest → ResponseOutparam → IO Unit)`,
  one instance per request.

```lean
def main : IO Unit := IncomingHandler.serve fun request out => do
  match ← request.consume with          -- IO (Except Unit IncomingBody)
  | .ok body => …
  | .error () => …
```

**Why.** These are the WIT's own semantics: its errors are values a program
handles, and resources have explicit lifetimes the host tracks. Rust's, C's
and Go's wit-bindgen output read the same way.

**Alternatives.** Throwing the WIT errors as `IO.Error` (loses their type);
freeing resources through Lean's reference counting (a handle's drop order
matters to the host: a stream before its body); renaming toward Lasm.JS.Web's
names (wasi:http is not the fetch API).

**Where.** 0.7.0 (#202), unchanged. Full rules: docs/WASI_FASTLY_BINDINGS.md,
"Mapping rules". **Status:** pending sign-off.

#### A31: hand-written helpers for whole bodies, and `respond`

**Decision.** A small hand-written module, `Lasm.WASI.Http.Respond`, imported
by `Lasm.WASI.Http`:

```lean
InputStream.readAll (s : InputStream) : IO (Except StreamError ByteArray)
OutputStream.writeAll (s : OutputStream) (bytes : ByteArray) : IO (Except StreamError Unit)
IncomingRequest.readBody (request : IncomingRequest) : IO ByteArray
respond (out : ResponseOutparam) (status : UInt16) (headers : Array (String × String)) (body : ByteArray) : IO Unit

def main : IO Unit := IncomingHandler.serve fun request out => do
  let body ← request.readBody
  respond out 200 #[("content-type", "text/plain")] s!"{body.size} bytes\n".toUTF8
```

**Why.** Every wasi:http program wrote these (the `fetch` template, Conduit
and examples/wasi-http each had a copy): `blocking-write-and-flush`
takes at most 4,096 bytes per call, and a body is a resource whose stream is
dropped before it is finished. The two stream helpers keep the WIT's error
values, as the calls they repeat do; `readBody` and `respond` make several
calls and throw an `IO.Error` naming the one that failed. `respond` checks
every header before the response is set, so a refused header sends nothing.
Streaming, trailers and outgoing requests stay on the generated calls.

**Alternatives.** Keeping it per app (Q31): the same 60 lines everywhere. A
whole `Request`/`Response` layer over wasi:http: that is what Lasm.Fetch was,
and Stage 0 removes it.

**Tests.** examples/wasi-http uses all four, under `wasmtime serve` in
wasi.yml. Docs: docs/WASI_FASTLY_BINDINGS.md, "Helpers".

**Where.** PR (this one), next release. **Status:** pending sign-off.

#### A32: Fastly errors stay `EIO FastlyStatus α`

**Decision.** Every Lasm.Fastly call stays an `EIO FastlyStatus α` action,
lifting into `IO` with the message `Fastly host call failed: <status>`;
`found?` maps `$none` to `Option.none`.

```lean
let agent ← found? (HttpReq.headerValueGet req "user-agent")    -- Option String
match ← (ConfigStore.get settings "color").toBaseIO with
| .ok color => …
| .error .none => …                                               -- a typed status
```

**Why.** The witx's every function returns `(expected T (error $fastly_status))`.
`EIO ε` is Lean's own typed-error `IO`: a program that does not care writes
plain `IO`, one that does matches the status. **Alternatives.** `IO α` with
the status only in the message (untyped); `IO (Except FastlyStatus α)`
everywhere (every call site unwraps).

**Where.** 0.7.0 (#194), unchanged. **Status:** pending sign-off.

#### A33: `send_v2`/`send_v3` stay unbound for now

**Decision.** The five functions that report a `$send_error_detail`
(`send_v2`, `send_v3`, `pending_req_poll_v2`, `pending_req_wait_v2`,
`pending_req_select_v2`) stay unbound; `HttpReq.send` and the v1
`pending_req_*` cover sending, and fail with the status alone.

**Why.** Binding them needs a second error type, `EIO (FastlyStatus × SendErrorDetail) α`,
and a generator rule for output records, for a detail (DNS, TLS or connection
error) that no Lasm app reads yet. They are listed with the reason in
scripts/bindings/fastly-surface.json. The trigger to bind them is the first
program that must tell a DNS failure from a refused connection.

**Alternatives.** Bind them now with the pair error type (Q33): a second
error type in one API before anyone needs it.

**Where.** 0.7.0 (#194), unchanged. **Status:** pending sign-off.

#### A34: Fastly keeps the witx layout, without dot-notation aliases

**Decision.** Fastly calls stay in one namespace per witx module, with the
witx's names: `HttpReq.methodGet req`, `KvStore.lookupWaitV2`. No aliases on
the handle types.

```lean
let method ← HttpReq.methodGet req
HttpResp.statusSet resp 200
```

**Why.** In witx a handle is a bare `(handle)` type, not a resource with
methods; the functions belong to modules (`fastly_http_req.method_get`). The
Lean names are those, one to one, so the ABI's documentation reads directly.
WASI's dot notation (A30) comes from WIT resources, which witx does not have.
Aliases would give every call two names.

**Alternatives.** Generated aliases (`req.methodGet`): a second spelling of
244 functions; renaming to methods on handles: departs from the ABI.

**Where.** 0.7.0 (#194), unchanged. **Status:** pending sign-off.

### Lasm.JS core

#### A6.1: the project's own JavaScript files, `@[js "./ffi/x.mjs" "f"]`

**Decision.** Option 1A of [LASM_JS_GAPS.md](../../proposals/LASM_JS_GAPS.md): a
binding's module may be a path starting with `./` or `../`, an ES module file
(`.mjs`) relative to the Lean file that declares the binding. No new syntax
and no new API.

```js
// ffi/stream.mjs, next to Server.lean
import { status } from './lib/status.mjs';
export function writeAndEnd(res, body) { res.writeHead(status); res.end(body); }
```

```lean
@[js "./ffi/stream.mjs" "writeAndEnd"] opaque writeAndEnd : Value → Data → IO Unit
```

Lean records the binding under the file's path from the declaring module's
source root (`./App/ffi/stream.mjs` for module `App.Server`), so the same file
named from two Lean files is one module. `lasm build` resolves the file
against the Lean file's directory, adds the files it imports by relative path,
and ships them with the program: `host/project-modules/` on Node,
`lasm/project-modules/` on the edge targets, Bun and Deno (imported by the
generated entry module), and `project-modules/` beside the browser loader (an
unbundled module the loader imports). The binding check loads the file. The
files' contents are part of the build's identity.

**Why.** It is how Gleam (`@external(javascript, "./ffi.mjs", "f")`),
PureScript (a foreign module beside the source) and wasm-bindgen
(`module = "/js/foo.js"`) do it: real files, with editor support, linting and
tests, and nothing evaluated from strings, so it works on Cloudflare Workers
and under a strict Content-Security-Policy. Before, the same needed a local
`file:` npm package and `npm install`.

**Limits.** The file is an ES module ending in `.mjs` (Node loads it with
`require(esm)`, so no top-level await), and it and its relative imports stay
beside or below the source root; the build refuses anything else, naming the
binding.

**Alternatives.** A `js_module` command with the JavaScript in a Lean string
(option 1B: no editor support; possible later on top of this), a `js%`
inline-expression elaborator (1C: the largest surface, and it encourages many
tiny host calls), run-time `eval` (1D: refused by Workers and CSP).

**Tests.** test/project-modules.test.mjs (resolution, imports, refusals);
test/fixtures/js-core on Node 26 and 24, Bun, Deno, Workers and Chromium
(web-bindings.yml). Docs: docs/JS_BINDINGS.md, "Your own JavaScript files".

**Where.** PR (this one), next release. **Status:** pending sign-off.

#### A6.2: JavaScript classes from Lean, `Lasm.JS.Class.define`

**Decision.** Option 2B of [LASM_JS_GAPS.md](../../proposals/LASM_JS_GAPS.md): a
small builder in its own module, `Lasm.JS.Class` (not imported by `Lasm.JS`),
over a builtin JavaScript module, `lasm:class`, that makes a real
`class … extends Base` without `eval`.

```lean
inductive Class.Method where
  | sync (f : Value → Array Data → IO Data)      -- this, args
  | async (f : Value → Array Data → Async Data)  -- returns a promise
structure Class.Spec where
  name : String
  extends? : Option Value := none
  constructor : Option (Value → Array Data → IO Unit) := none   -- after super(...args)
  methods : Array (String × Class.Method) := #[]
  getters : Array (String × (Value → IO Data)) := #[]
  statics : Array (String × Data) := #[]
def Class.define (s : Class.Spec) : IO Value      -- the class (its constructor)

let c ← Class.define {
  name := "Counter", extends? := some (← errorClass)
  constructor := some fun self _ => self.set "count" (0 : Nat)
  methods := #[("increment", .sync fun self _ => do
    let n := (← self.get "count" Nat) + 1; self.set "count" n; return toJS n)] }
```

**Why.** It is the smallest addition that turns "write JavaScript for every
class" into a Lean definition, on every JavaScript target, and keeps sync
versus async explicit per method, which the semantics need (a DOM lifecycle
callback cannot wait). `this` reaches Lean as the first argument of the
underlying functions, so no host change was needed. A6.1's project files
remain the escape hatch for anything else.

**Not covered.** Classes a platform looks up by export name when the module
loads (Durable Objects, Workers RPC entrypoints): option 2D, a build-time
exported class, designed with the Workers entry module (the 0.5 stream's
Durable Objects; A28).

**Alternatives.** 2A, only project files (every class needs JavaScript);
2C, `deriving JSClass` sugar (a larger elaborator surface, revisit once 2B
has users); 2E, Proxy-based fakes (`customElements.define`, `instanceof` and
`super` need a real class).

**Tests.** test/lasm-class.test.mjs; test/fixtures/js-core's "classes"
section on every JavaScript target (a class extending `Error`, used from
JavaScript and from Lean). Docs: docs/JS_BINDINGS.md, "JavaScript classes".

**Where.** PR (this one), next release. **Status:** pending sign-off.

#### 0.6-4: `@[js]` records its binding without an attribute of its own

**Decision.** `@[js "module" "export"] opaque f : T` is elaborated by a
command elaborator in `Lasm.JS.Meta` that defines `f` and records the binding


#### A27.1: `Async.toPromise`, reviewed for the Lasm.JS core

**Decision.** The 0.5 stream's `Lasm.JS.Async.toPromise [ToJS α] (act : Async α) : IO Value`
(PR #216, A27) fits the core as it is: a JavaScript promise of a Lean
computation that starts at once, for APIs that take a promise of work still
running (Workers' `ctx.waitUntil`).

```lean
ctx.waitUntil (← Async.toPromise (kv.put "k" v))
```

**Review notes.** It is `Function.ofFn` plus one call, so it costs two host
calls and a function JavaScript releases once the promise settles, with
`ofFn`'s semantics (no Lean thread held while it waits, a Lean error rejects
with an `Error`). It is written `Async.toPromise act`, not `act.toPromise`:
dot notation on `Async` would need a definition in Std's namespace. No change
requested.

**Where.** PR #216 (0.5 stream). **Status:** pending sign-off.
#### A4: `Function.ofFn` sets the JavaScript function's `length`

**Decision.** Every function maker takes `(length : Nat := 0)`; `ofFn1` sets 1,
`ofFn2` and `ofSyncFn2` set 2. The host sets it with
`Object.defineProperty(f, "length", …)` when it creates the function (op 210's
argument carries it above the kind byte), so it costs no extra host call.

```lean
Function.ofFn (f : Array Data → Async Data) (length : Nat := 0) : IO Value
Function.ofFnReply (f : Array Data → Async Function.Reply) (length : Nat := 0) : IO Value
Function.ofSyncFn (f : Array Data → IO Data) (length : Nat := 0) : IO Value
Function.ofFn1 (f : α → Async β) : IO Value                    -- length 1
Function.ofFn2 (f : α → β → Async γ) : IO Value                -- length 2
Function.ofSyncFn2 (f : α → β → IO γ) : IO Value               -- length 2

-- An Express error handler: Express recognises it by its four parameters.
let onError ← Function.ofFn (length := 4) fun args => do …
```

**Why.** JavaScript callers read `length`: `Deno.serve` calls a handler of
length 0 without its request, and Express treats only a four-parameter
function as an error handler. A JavaScript function declares its parameters,
so the native shape is a function whose `length` is its arity. The default
stays 0 (a variadic function, which `(...args)` also reports), so existing
programs behave the same, except that `ofFn1`/`ofFn2`/`ofSyncFn2` handlers
now report their arity.

**Alternatives.** Leave it at 0 and document it (Q4 b): every API that reads
`length` stays unusable from Lean. Infer the length from `f`: `f` takes an
`Array Data`, so there is nothing to infer from. A separate
`Function.withLength` call: one more host call per function, and easy to
forget.

**Tests.** `test/node-js.test.mjs` and `test/edge-js.test.mjs` (op 210);
`test/fixtures/js-interop` (`lengths: 0 1 2 3`, installed acceptance on
Linux, macOS and Windows). Docs: docs/JS_BINDINGS.md, "Callbacks".

**Where.** PR (this one), next release. **Status:** pending sign-off.

#### A5: the binding check warns about globals the build's target provides

**Decision.** `lasm build`'s binding check still runs on Node. A
`@[js "globalThis" "…"]` export that Node lacks fails a Node build as before,
and is a warning when the build's target is another runtime (`--target deno`,
`bun`, `workers`, `deno-deploy`, `vercel-edge`, `netlify-edge`,
`supabase-edge`, `browser`):

```lean
@[js "globalThis" "Deno.serve"] opaque denoServe : Value → IO Value   -- builds for --target deno
```

```
[lasm] Lasm.JS binding warning: Main.denoServe: globalThis export "Deno.serve" is missing where Lasm checks bindings; it must exist on deno
```

**Why.** A global belongs to the runtime the program targets: Deno's `Deno`,
the browser's `document`. Checking it against Node is checking the wrong
runtime. Other errors (an export that is not a function, a module that is not
installed) stay errors on every target. Option (b) of Q5.

**Alternatives.** (a) Warn on every target: hides a real mistake on Node.
(c) Leave it: hand-written bindings of Deno, Bun, Workers or browser globals
cannot build, which pushes programs to dynamic `global.get` chains. Running
the check on the target runtime: Lasm does not install Deno or a browser to
build.

**Tests.** `test/application-binding-check.test.mjs`,
`test/cli-dispatch.test.mjs`. Docs: docs/JS_BINDINGS.md, "Binding check".

**Where.** PR (this one), next release. **Status:** pending sign-off.

#### A8, A47, A48, A49, A50: the core shapes confirmed

**Decision.** Kept as they are (A8 is the three below, A47–A49):

- **A47.** `get`/`set` take any `[ToJS κ]` key: `o.get "rows"`,
  `o.get (2 : Nat)`, `o.get symbolValue`, as JavaScript's `o[key]` (#170,
  0.6.1).
- **A48.** A wait inside a synchronous callback (`ofSyncFn`) that needs the
  JavaScript event loop fails at once with an error naming the wait (#122,
  0.5.0). JavaScript's caller is blocked on the callback, so the promise
  could never settle; serving other host calls meanwhile would run unrelated
  JavaScript in the middle of the caller.
- **A49.** `ofSyncFn` has no fire-and-forget `Async`: starting background
  work is explicit (`Value.toTask`, a Lean task), so a synchronous callback
  never silently drops a computation.
- **A50.** `Lasm.JS.Wire.encode : Data → Except String ByteArray` (#154,
  0.6.1): a value whose length does not fit the wire's u32 is an error, not a
  wrapped length.

```lean
let tag ← (← global).get "Symbol" >>= (·.callMethod "for" #[toJS "lasm.tag"])
box.set tag "tagged"                                 -- A47
let f ← Function.ofSyncFn fun _ => do
  let p ← lib.callMethod "later" #[]
  p.await String                                     -- A48: fails at once, catchable
```

**Why.** Each is what JavaScript itself does (any property key; run to
completion) or makes a failure explicit instead of silent. **Alternatives**
are in REVIEW.md §1: String-only keys, waits that hang or deadlock, an
implicit background `Async`. **Tests.** `test/fixtures/js-interop` (keys),
`test/fixtures/js-sync-waits`, `test/lasm-js-framing.test.mjs`.

**Where.** Shipped in 0.5.0 and 0.6.1. **Status:** pending sign-off.

### Lasm.RPC

#### 0.6-13: Lasm.RPC is dropped (Jordan, 2026-11-16)

**Decision.** Lasm.RPC is deleted. A Lean app's server and browser share
plain Lean types and talk plain REST over each host's own fetch API
(Lasm.JS.Web's `fetch`, `Request` and `Response`; Lasm.Fastly; Lasm.WASI.Http).
Validation is a subtype the shared module declares, so a handler that needs a
valid value demands it in its type:

```lean
-- Shared.lean
def ValidTitle := { t : String // checkTitle t = .ok () }
structure NewTodo where
  title : String
  deriving ToJson, FromJson

-- Server: the route parses, validates once, and hands on the subtype.
def addTodo (t : ValidTitle) : Async Todo := …
```

**Why.** Every host already has a native way to serve and call HTTP, and
REST with shared types is what those hosts and their tools expect. RPC's one
guarantee, the validation proof reaching the handler, is a subtype, which
needs no library.

**Alternatives.** Keeping Lasm.RPC with a transport-free `dispatch` and
`Lasm.RPC.webHandler` (PR #303, closed unmerged).

**Where.** Decided 2026-11-16. The library is deleted, and Conduit's and
Ledger's frontends move off `Endpoint.call`, once Lasm.UI is decided (their
`call` commands are Lasm.UI commands). **Status:** pending sign-off.

#### A37, A38: dropped with Lasm.RPC

**Decision.** No `dispatch`, `webHandler` or `serve'` naming question
remains: they are dropped with Lasm.RPC ([0.6-13](#06-13-lasmrpc-is-dropped-jordan-2026-11-16)).
PR #303, which built `dispatch` and `webHandler`, was closed unmerged.
**Status:** pending sign-off.

### Lasm.UI

#### 0.6-8: Lasm.UI is cut to its core (Jordan, 2026-11-16)

**Decision.** Lasm.UI keeps what only a UI framework can do: `Html` and
`html!`, the proved diff and applier, the app loop (`init`, `update`, `view`,
`subscriptions`), events and decoders, URL changes and routing, SSR and
hydration. Its own wrappers of browser APIs are removed. The app loop's own
effects stay data; everything else is one generic command over the generated
browser bindings:

```lean
inductive Effect (Msg : Type) where
  | msg (msg : Msg)
  | delay (ms : Nat) (msg : Msg)
  | navigate (url : String) (replace : Bool)        -- Cmd.pushUrl / replaceUrl
  | task (run : (Msg → IO Unit) → Async Unit)

def Cmd.task (run : Async Msg) : Cmd Msg
def afterFrame : Async Unit                          -- the next frame is on screen

| .load, m => ({ m with loading := true }, Cmd.task do
    let r ← Lasm.JS.Web.fetch (.usvString "/api/items")
    return .loaded (← r.text))
```

Removed: `Http` (`Request`, `Response`, `Error`, `get`, `post`, `request`),
`Storage`, and the commands `now`, `randomBytes`, `randomNat`, `back`,
`forward`, `load`, `storageSet`/`Get`/`Remove`, `focus`, `blur`, `title`,
`port` and `io`, with their `lasm:ui-dom` exports. Each is a few lines of
`Cmd.task` over `Lasm.JS.Web.Browser` (`fetch`, `localStorage`,
`crypto.getRandomValues`, `history.go`, `location.assign`, `document.title`),
or `Mount.port` for ports. The migration table is in docs/release/next-notes.md.

`Cmd.task` takes the platform's own shape for a browser action, an `Async`
computation (the web's promise-returning APIs, awaited without holding a
thread), and delivers the message it returns. Its effect is in
continuation form, `(Msg → IO Unit) → Async Unit`, so one action can deliver
no message, one, or a stream, and `Cmd.map` stays definitional: the proved
`cmd_map_comp`, `cmd_map_id`, `cmd_map_effects` and `cmd_map_batch` keep their
proofs unchanged. `Cmd.pushUrl` and `replaceUrl` stay because routing is the
loop's: they make the history entry with the frame that shows the new page and
run `onUrlChange`, which a bare `history.pushState` would not. `afterFrame`
stays because only the loop knows when its frame is on screen (focusing an
element the update just added).

Apps that want effects they can inspect in tests and proofs declare their own
effect data and interpret it with `Cmd.task` (docs/UI.md, "Effects you can
test"); examples/ui/todomvc does, and proves what its `update` saves
(`Todo.update_saves`).

**Alternatives.** Keeping UI's wrappers as pure data (A35's recommendation
before this decision): a second, smaller copy of the web platform to keep
current. `Cmd.task : Async Msg → Cmd Msg` alone, without the continuation
form: `Cmd.map` would need the functor laws of `Async`, which Std does not
provide, and streams would need another effect.

**Tests.** The proofs above (library-proofs.yml); test/ui/DocsTest.lean (the
guide's examples); examples/ui/demo (HTTP, focus and ports through
`Cmd.task`) and examples/ui/todomvc (storage and focus) in the browser suite
(ui.yml); test/ui-dom.test.mjs (`afterFrame`).

**Where.** PR (this one), next release (breaking). The example apps pinned
to a published `@lasm/cli` (Conduit, Ledger, Tandem, Porter, Folio) move to
`Cmd.task` with the version bump that moves their pins. **Status:** pending
sign-off.

#### A35: UI's own `Http`, `Url` and `Storage`

**Decision.** `Http` and `Storage` are removed (0.6-8): the generated
`fetch` and `localStorage` replace them through `Cmd.task`. `Url` stays: it is
the type `onUrlChange` and `init` hand the app, pure data that routing code
matches on and proofs reason about (`Url.parse`, `segments`, `param?`,
`Url.build`).

```lean
def route (u : Url) : Page :=
  match u.segments with
  | ["items", id] => .item id.toNat!
  | _ => .home
```

**Why.** `Url` is the app loop's routing input, not a wrapper of a browser
call. **Alternatives.** Lasm.JS.Web's `URL` for routing: a handle, so a pure
`view` and `route` could not use it, nor a proof.

**Where.** PR (this one). **Status:** pending sign-off.

#### A36: the `_` suffix names stay

**Decision.** Names that clash with Lean keywords or core names keep a
trailing underscore: `class_`, `main_`, `id_`, `type_`, `for_`, `section_`.
`html!` uses the plain HTML names (`<main class="…">`), so only the function
DSL sees the suffix.

```lean
main_ [class_ "app"] [section_ [] [text "…"]]
html! <main class="app"><section>…</section></main>
```

**Why.** It is the common convention in Lean and the Elm-family libraries
(Elm's `Html.Attributes.class` needs no suffix only because Elm has no
`class` keyword). «guillemets» (`«class»`) are Lean's escape for an
identifier, not meant for everyday calls, and they are hard to type.

**Alternatives.** «guillemets»; a prefix (`hClass`); a namespace per kind
(`Attr.class`, still a keyword clash).

**Where.** Unchanged since Lasm.UI shipped. **Status:** pending sign-off.

#### A56.1: Lasm.UI stays in `@lasm/cli` for now (Jordan, 2026-11-16)

**Decision.** Lasm.UI keeps its name and ships inside the core package,

**Why.** Jordan's call: the split adds a resolution mechanism and a release

**Where.** Decided 2026-11-16. **Status:** pending sign-off.

#### 0.6-8 (continued): `Url.percentDecode` returns `Option String`

**Decision.** `Lasm.UI.Url.percentDecode : String → Option String` keeps its
`Option`: `none` when the escapes do not decode to UTF-8 (`%FF`), so routing
code sees a malformed URL instead of a guess. `Lasm.Fetch.percentDecode`, which
returned the input unchanged instead, is deleted with Lasm.Fetch (0.2), so the
inconsistency the inventory noted goes with it.

```lean
#guard Url.percentDecode "caf%C3%A9" == some "café"
#guard Url.percentDecode "%FF" == none
```

**Where.** Unchanged since Lasm.UI shipped. **Status:** pending sign-off.

#### 0.6-9: `html!`'s helper terms stay

**Decision.** `html!` expands `{t}` to `lasm_children% t` (children) and
`lasm_attrs% t` (attributes), two term elaborators that fit `t` to a list by
its type, so the message type flows from the context into nested `html!` and
lambdas. They stay public syntax: a macro can only expand to syntax that
parses, and Lean's own elaboration helpers work the same way (`binop%`,
`unop%`, `leftact%`). Their names say they are Lasm's; nobody writes them.

**Alternatives.** Type classes (`ToChildren α Msg`) instead of the elaborator:
the message type would no longer flow into lambdas inside `{…}`, and the
error messages would be about instances, not the markup.

**Where.** Unchanged since `html!` shipped. **Status:** pending sign-off.
