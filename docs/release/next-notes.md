# Lasm (next release)

Notes for the next release, collected as changes land. They move to
`docs/release/<version>-notes.md` when the version is cut.

Mutation testing now covers every JavaScript module under `src/` (docs/TESTING.md, "Mutation testing"); the fixes its new tests found are marked *(mutation testing)* below.

## Improvements

- **Lasm.JS reads and writes Symbol-keyed properties.** `Value.get` and `Value.set` take a key of any type with `ToJS`, as JavaScript's `o[key]` does: a `String` (unchanged), a number (`o.get (3 : Nat)`), or a Symbol `Value` (`Symbol.iterator`, `Symbol.for "k"`). An array key is its string, as in JavaScript; `getFields` still takes strings. Source compatible: existing calls compile unchanged. *API change for Jordan's review:* `get [ToJS κ] (o : Value) (key : κ) …` and `set [ToJS κ] [ToJS α] (o : Value) (key : κ) (x : α)`, previously `(key : String)`. See docs/JS_BINDINGS.md, "Property keys".

## Fixes

- **Edge targets: a C-stack overflow traps at once instead of overwriting static data (#126).** The edge link (every `--target` built on the edge runtime: Workers, Deno, Bun, Vercel and Netlify Edge, Supabase, the browser) placed Lean's 1 MiB C stack above the program's static data, with nothing between them. A recursion that used up the C stack before the engine's own stack ran out (unoptimized code, or large frames) kept writing below the stack, over that data, and what happened next depended on what it overwrote: usually a trap, sometimes a wrong `call_indirect`, and on Bun a loop that never ended (the `edge-O0-bun` hang in CI). The stack now comes first in linear memory (`--stack-first`, as the WASI target already does), so an overflow runs below address 0 and traps on its first access, and the instance stops with `Stack overflow: the program used all of its 1 MiB C stack (deep recursion?)`. The Node link driver's edge recordings (both the JSPI and the Asyncify link) were updated to match emcc's link byte for byte.
- **A failing SDK archive decoder is reported as itself.** *(mutation testing)* When the managed Python's decoder for `.tar.xz` and `.zip` compiler SDK archives failed, could not start, or was killed, the tar parser's `TAR_BAD_ARCHIVE: Unrecognized archive format` for the empty stream it left was reported instead of the decoder's exit status and messages. The decoder's own error (`SDK archive decoder failed (<code or signal>): <its last messages>`, or the spawn error) is reported now.
- **A browser app loads when its server sends `application/wasm` with parameters.** *(mutation testing)* The loader took WebAssembly's streaming compilation for any `Content-Type` that began with `application/wasm`, but `WebAssembly.compileStreaming` accepts exactly `application/wasm`, so a server that sent, for example, `application/wasm; charset=binary` made the app fail to start instead of using the buffered path meant for unusual types. Only an exact `application/wasm` (any case) streams now.
- **`app.send`, a port's `send` and messages queued before Lean's handler reject instead of throwing.** *(mutation testing)* A `Lasm.Web.App` message or port handler that threw synchronously threw out of `send` at the JavaScript caller (and, for messages sent before Lean registered its handler, out of Lean's `onMessage`, leaving the queued messages' promises unsettled). The caller's promise now rejects with the handler's error, and every queued message is delivered.
- **A failing async Lean event handler is reported once.** *(mutation testing)* `lasm:web`'s listeners report a handler's rejected promise to the app; the promise was also handed back to the event target, and Node's `EventTarget` (edge and server targets) turns a listener's rejected promise into an uncaught exception. The listener now hands back a promise that does not reject.
- **`Lasm.Web.Canvas.draw` rejects every unknown command.** *(mutation testing)* A command named like an `Object` method (`constructor`, `toString`) was run as one instead of failing with "unknown drawing command".
- **A browser build into `public/` leaves nothing behind.** *(mutation testing)* `lasm build --target browser --output public/dist` was refused, as it should be, but only after its staging directory had been created inside `public/`, where the next build then found it.
- **`lasm build --target workers` no longer keeps a generated `workers/wrangler.toml` once the project has its own.** *(mutation testing)* A project that added `wrangler.toml`, `wrangler.json` or `wrangler.jsonc` at its root after an earlier build still had the earlier generated `workers/wrangler.toml` when the program had not changed (an unchanged rebuild keeps the output directory as it was). It is now removed, as a build from scratch leaves none.
- **macOS network interfaces report the right hardware (MAC) address.** *(mutation testing)* The Node host read the link-layer address of `Std.Net.interfaceAddresses` at the wrong offset of macOS's `sockaddr_dl` (after `sdl_alen` bytes of the name instead of `sdl_nlen`), so an interface such as `en0` reported bytes of its name and address mixed. It now follows libuv's `LLADDR`.
- **`lasm package` says why it refuses more than 65,535 files.** *(mutation testing)* A function package with more entries than a ZIP's 16-bit count holds failed with Node's `RangeError` about an out-of-range value instead of "Function package has more than 65535 files"; the check now comes before any record is written.

## Repository

- **Unused code and dependencies removed (no behaviour change).** The repository no longer depends on `binaryen`, `@yarnpkg/cli-dist`, `pnpm` or `miniflare` (about 400 MB less `node_modules` per checkout and CI job), and the Lean 4.32 `lean/` (`Lasm.IO`) and the unused `runtime/host.cpp`, `core.cpp`, `stack.cpp` and `tasks.inc.cpp` are deleted. The published `@lasm/cli` is unchanged.
