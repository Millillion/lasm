# Draft: publishing `@lasm/cli` 0.1.0 (Phase 5.4)

**Status: DRAFT, awaiting the user's approval. Nothing here has been run.** No npm
package, git tag or GitHub release exists for 0.1.0. Phase 5.3 (release gate)
prepared this page; the evidence is in [PLAN.md](../PLAN.md) (5.3) and
[PROGRESS.md](../PROGRESS.md).

**0.1.0 goes out through the automated release process** ([RELEASING.md](../RELEASING.md),
user decision 2026-10-24): after the one-time npm bootstrap, a release PR sets
`package.json` `version` to `0.1.0` and adds [0.1.0-notes.md](0.1.0-notes.md);
`release-checks` runs the candidate checks and the npm rehearsal for that commit;
on merge (only with the user's explicit go-ahead for 0.1.0), `release.yml`
publishes with npm trusted publishing and provenance, verifies `npm create
lasm@0.1.0`, tags `v0.1.0` and creates the GitHub release. Nobody publishes by hand.

## Decisions for the user

1. **Licence of `@lasm/cli`.** The packed candidate says `UNLICENSED`
   (`scripts/package-node-release.mjs`); the repository `LICENSE` is MIT. Proposed:
   publish as MIT (`--license MIT`, below).
2. **Tool packages on npm or CLI only.**
   - *A (proposed, the tested design):* publish the 21 tool packages, the CLI and
     `create-lasm`.
     `npm install @lasm/cli` then brings Lean and the build tools through npm (about
     340 MB on Linux x64), honouring the user's registry, proxy and cache.
   - *B:* publish only `@lasm/cli` with its tool pins removed; every tool is
     downloaded from GitHub releases on the first build (the path every acceptance
     run uses today). Needs a packaging change and its own loopback check.
3. **Git: decided (user, 2026-10-23): system Git.** Lasm ships and downloads no
   Git; Lake projects with dependencies need the `git` on PATH, and Lasm stops
   with the install command when it is missing ([system Git](../MANAGED_GIT.md)).
4. **Account security: decided (user, 2026-10-24): trusted publishing.** No npm
   token exists. `release.yml` publishes through OIDC with `--provenance`; each
   package trusts only Millillion/lasm `release.yml` (no environment). The owner's
   account (2FA) is used once, for the bootstrap ([RELEASING.md](../RELEASING.md)).
5. **Dist-tag:** `latest` for a normal version such as `0.1.0` (0.x already signals
   an early release), `next` for a prerelease. New tool package versions get the
   same tag; the CLI pins exact versions, so nobody installs them by tag.

## How 0.1.0 is released

All of it runs in GitHub Actions ([RELEASING.md](../RELEASING.md)); the user runs
only the bootstrap, once, and gives the go-ahead to merge.

1. **Bootstrap (user, once):** `npm login` (2FA), then
   `node scripts/release/bootstrap-npm.mjs --dry-run` and
   `node scripts/release/bootstrap-npm.mjs`: a deprecated `0.0.0` placeholder for
   each of the 23 names and `npm trust github <pkg> --repository Millillion/lasm
   --file release.yml` for each.
2. **Release PR (agent):** `package.json` `version` `0.1.0`, the final
   [0.1.0-notes.md](0.1.0-notes.md) (`GATE_SUMMARY` filled in), and the README change
   that makes `npm create lasm` / `npm install @lasm/cli` the primary install path
   and marks 0.1.0 as the verified release.
3. **`release-checks` on the PR:** candidate build and five-platform acceptance,
   platform-support, templates, js-interop-examples, and the loopback rehearsal of
   all 23 packages with `version=0.1.0 license=MIT`.
4. **Merge after the user's go-ahead.** `release-checks` repeats for the merge
   commit; then `release.yml` rebuilds the packages, checks them byte for byte
   against the rehearsal, publishes the 21 tool packages, `@lasm/cli@0.1.0` and
   `create-lasm@0.1.0` (`--tag latest --provenance`), verifies `npm create
   lasm@0.1.0 app -- --template hono` from the public registry (install, build,
   server, HTTP 200), tags `v0.1.0` and creates the GitHub release from the notes.

`npm publish` cannot be undone after 72 hours, and a published version number can
never be reused; if a step fails half-way, re-run the workflow: it publishes only
what is missing and never republishes ([recovery](../RELEASING.md#recovering-from-a-partial-failure)).
